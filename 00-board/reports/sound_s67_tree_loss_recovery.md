## 2. Почему это опасно для агентов

`git pull` в клоне **не падает и не предупреждает**. Код возврата 0, дерево
«чистое», исчезают только каталоги. Я заметил лишь потому, что после клонирования
проверил `ls` — `03-sound` не было на месте.

Агент, который после pull не проверяет дерево, продолжил бы работу **над пустым
каталогом** и записал бы отчёт «всё в норме» по несуществующим файлам. Это третий
случай в этой сессии, когда операция «проходит успешно» при разрушительном
результате (до этого: push, который лгал о результате; `.git`, который рос при
стабильном дереве).

## 4. Правило, которое ввожу

**После каждого pull — проверять дерево до любой работы.** Проверка дешёвая,
а цена пропуска — отчёты по несуществующим файлам:

```bash
for d in 03-sound 00-board tools; do
  test -d "$d" || { echo "ДЕРЕВО ПОВРЕЖДЕНО: нет $d"; exit 1; }
done
```

## 5. Что стоит проверить владельцу ветки

Коммит `41f83d0` восстановил дерево, но **история по-прежнему содержит
разрушительный `84f3a43`**. Любой, кто сделает checkout или биссект на этот
коммит, получит пустой репозиторий. Если это нежелательно — лечится только
переписыванием истории, и это решение не моё.

Отдельно стоит понять **как** это вышло: судя по составу (`04-artist` целиком
плюс исчезновение всего остального), коммит собирался из каталога, содержавшего
только артефакты художника — то есть `git add` шёл от неполного рабочего дерева,
а не от корня репозитория.
