**Дата:** 2026-11-27 · **Команда:** тег `v3.8.0` → Release на SHA `26edbeef…` с asset ZIP
· **Итог:** тег и jar исправлены и **проверены побайтово**; asset ZIP не загружен (сеть)

## 1. Уточнение по команде — без него тег встал бы не туда

`26edbeef…` — **не SHA коммита**, а **sha256 пакета**:
`26edbeefa9dc40fcaf29d0d32b2dd65483678d8fb0fc7577f656af13886ea07c`
(16 994 843 Б, 1037 файлов, `mod_version=3.8.0`).

Коммита `26edbeef` в репозитории нет ни в одной ветке (`git cat-file -t` → нет).
Коммит, в котором лежит пакет: **`b91153c`** — проверено
`git cat-file -p b91153c:01-coder/3.8.0/…zip | sha256sum` → `26edbeef…`.

## 2. Что было до команды — и что я нашёл

Тег `v3.8.0` стоял на `4e66645d` — коммите бота «build: carnis-3.8.0.jar
(run 45857171374)». В том коммите **ZIP вообще нет**, только jar.

Хуже: jar был собран из пакета **`e08c9b13…`** — а это пакет **до** перерисовки
звука Звуком. Между `a1cc56e` (откуда шла сборка) и `b91153c` изменены
**6 `.ogg`**: `combat_flesh_hit_01/02/03` и `hive_spread_01/02/03`.

То есть **в релизе играл старый звук** — тот самый `flesh_hit`, ради которого
перерисовывали crest по находке Ревизора r29.

## 3. Почему в `main` был jar от 3.7.3

Прогон `45861521460` (16:46) собрал `carnis-3.7.3.jar`, а не 3.8.0. Причина
документальна: на коммите `f2ce9a14` вердикт `reviewer_380_verdict.md`
содержал **`# НЕ ПРИНЯТО`** (байты `e08c9b13…`, пакет старше правок Звука).
CI выбирает первый каталог по убыванию с неотрицательным вердиктом — 3.8.0 был
отклонён, и он честно взял 3.7.3.

**Это правильное поведение CI.** Не «CI сломался», а «3.8.0 тогда был не принят».

**Тег в итоге на `be5fdb5`, а не на `b91153c`** — и это не сбой: шаг публикации
в `.github/workflows/build.yml` штатно выполняет `git tag -f` на коммит,
содержащий собранный jar. Коммит пакета (`b91153c`) — предок `be5fdb5`.
Просто «тег на коммите с пакетом» и «тег на коммите с jar» — разные вещи,
и workflow выбирает второе.

## 6. Asset ZIP — почему не залился

```
uploads.github.com   → 000  (SSL_ERROR_SYSCALL)
api.github.com       → 200
github.com           → 200
```

GitHub принимает asset'ы **только** через `uploads.github.com`. Хост в песочнице
недоступен на уровне TLS. Пять попыток разными способами (`gh release upload`
×4, прямой `curl` на `upload_url` из API) — один и тот же EOF.

**Это исчерпание сети, а не прав и не «не попробовал».**

Чтобы дозалить, нужно любое из:

1. **доступ к `uploads.github.com`** — команда готова, повторю сразу;
2. **вручную**: Releases → `v3.8.0` → Edit → Attach binaries.

Сверка после дозалива:

```
файл    project-3.8.0-clean.zip
размер  16 994 843 Б
sha256  26edbeefa9dc40fcaf29d0d32b2dd65483678d8fb0fc7577f656af13886ea07c
```

В коммите тега пакета **нет** (`main` не содержит `01-coder/3.8.0` — там 3.7.3,
760 файлов). Пакет доступен:

- в ветке ролей: `…/blob/arena/d474d740-carnis-hub/01-coder/3.8.0/project-3.8.0-clean.zip`
- на диске интегратора: `01-coder/3.8.0/project-3.8.0-clean.zip`

**Это остаточный риск:** релиз опубликован с jar, но ZIP-пакета в релизе нет,
а `main` его не содержит. Если пакет должен быть воспроизводим из релизного
коммита — нужен либо asset (сеть), либо вливание ветки в `main` (решение
Архитектора: 993 коммита расхождения).
