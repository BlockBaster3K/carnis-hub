## 3. Что осталось: если громкость не литерал, читается ПИТЧ

```
playSound(…, ev, SoundSource.HOSTILE, this.smashVolume(), 1.0F)
→ amalgam_smash   1.00   1.00   1.000   ok
```

Инструмент берёт **первый float после `SoundSource`** — а это `1.0F`, то есть
питч. `unparsed` не срабатывает, потому что float найден; просто не тот.
Реальная громкость метода не проверяется вообще.

**Насколько это живо в пакете** (мой разбор 77 вызовов с `SoundSource` в Java):

| | значение |
|---|---:|
| вызовов с `SoundSource` | 77 |
| громкость **не** числовой литерал | **9** |
| из них с литеральным питчем `1.0F` (то есть маскируется под «ok») | **9 из 9** |

Примеры: `HeartAmbientTicker.java` — реальная громкость `0.2F + proximity * 0.8F`
(от 0.2 до 1.0), `ScytheItem` — `soundVolume`, `CarnisCombatSounds` —
`pending.volume()`.

**Сегодня приёмку это не задевает:** все 4 события спеки, у которых есть вызов в
коде, передают литерал — `amalgam_smash 1.0F`, `creeper_rupture 1.0F`,
`synapse_shock 0.8F`, `hive.spread 0.65F`. То есть дефект **латентный, а не
действующий**. Но как только в спеку попадёт событие с вычисляемой громкостью
(а `hurt`/`combat`-события именно такие), чекер напечатает «ok» при любой
реальной громкости, пока питч равен `1.0F`.

**Правка на одну строку:** если аргумент в позиции громкости не числовой
литерал — класть его в тот же `unparsed`, что и полностью неразобранную форму,
то есть отказ (код 3), а не переход к следующему числу.
