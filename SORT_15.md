## 2. ⛔ Критическая находка: `Commit jar` пушит ветку в `main`

### 2.1. Где срабатывает

Наш workflow триггерится на `push` в `01-coder/**`. **Мы всегда пушим в рабочую ветку `arena/…`, а не в `main`.** Значит job выполняется на коммите **ветки**, и `actions/checkout` даёт HEAD ветки. Дальше шаг делает:

```bash
git push origin HEAD:main
```

`HEAD` — это ветка, а не `main`. Команда проталкивает **всю ветку** в `main`.

### 2.2. Симуляция (сделал на копии репозитория)

```
ДО:    main = base A                    (файлы: a.txt)
       ветка = base A → недо деланная фича → коммит jar

прогон на ветке:
   git push origin HEAD:main  отправляет:
      847c7ab build: carnis.jar (run 123)
      b8d7ede недоделанная фича      ← вот это

ПОСЛЕ: main = base A → недоделанная фича → коммит jar
       файлы в main: 06-build/  a.txt  secret.txt
```

**`git pull --rebase --autostash origin main` не спасает** — `main` является предком ветки, поэтому выдаёт `HEAD is up to date` и ничего не отсекает.

### 2.3. Почему это важно именно для нас

Наш процесс: правки → пуш в `arena/…` → CI → **PR → merge**. Этот шаг **ломает третий этап**: содержимое ветки попадает в `main` **напрямую, без PR и без вашего контроля**, в момент прогона CI.

Хуже: прогон запускается **сразу после пуша**, то есть `main` получает состояние ветки, которое вы ещё не смотрели.

### 2.4. Проверка защиты

- `rulesets` → `[]` — **правил нет**;
- `branches/main/protection` → **403**, но при моём `admin: true` это почти наверняка значит «защита не настроена» (при включённой защите эндпоинт бы ответил 200).

**Вывод: `git push origin HEAD:main` пройдёт.**

### 2.5. Петли не будет — это вы угадали верно

Проверил триггеры: `push.paths` → только `01-coder/**`. Коммит трогает `06-build/jars/` ⇒ повторного прогона не будет.

**Но:** если в `main` протолкнутся коммиты ветки, среди них будут правки в `01-coder/**` ⇒ **этот** push даст **второй** прогон на `main`. Он уже отработает по `main`, добавит jar и закоммитит только в `06-build/**` ⇒ третьего не будет. **Два прогона вместо одного.**

## 3. Как это исправить (одна строка)

Шаг должен коммитить **только файл jar**, поверх `main`, а не поверх ветки:

```bash
- git pull --rebase --autostash origin main
- git push origin HEAD:main
+ # коммитим на вершину main, а не текущей ветки
+ git fetch origin main
+ git checkout -B main origin/main
+ git add "06-build/jars/${{ steps.jar.outputs.name }}"
+ git commit -m "..." || echo "нечего коммитить"
+ git push origin main
```

(порядок `add`/`commit` — уже после переключения на `main`).

## 5. Уточнение по росту репозитория

Вы пишете «+12 МБ за прогон». Точнее так:

- имя файла фиксировано версией (`carnis-3.5.1.jar`), поэтому в рабочем дереве файл **перезаписывается** — визуально один файл;
- но git хранит **каждую версию блоба в истории** ⇒ `.git` растёт на **~12 МБ за прогон** даже при том же имени.

**Практическое следствие:** `git clone` тянет всю историю. После 10 прогонов клон ≈ 120 МБ. Для канала «клон» это заметно.
