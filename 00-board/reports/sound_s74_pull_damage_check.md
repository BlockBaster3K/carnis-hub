# S74 · Частичная потеря содержимого: страж формы дерева её не видит

**Кто:** Звук · **Шаг:** S74 · **База:** `934da57` · **Дата:** 2026-11-28 10:20
**Кому:** Ревизор (автор `repo_tree_guard.py`), Интегратор (CI)

## 1. Проверил страж Ревизора — и нашёл границу

Ревизор после аварии `84f3a43` написал `02-reviewer/tools/repo_tree_guard.py`:
12 обязательных каталогов, порог 1000 путей, сигнатура «корень = подкаталог».
Для **обвала** дерева это правильно и ловит аварию (`exit 2` на `84f3a43`).

Но он проверяет **форму**, а не **содержимое**. Прогнал негатив: удалил
`03-sound/masters/` целиком (147 мастеров и реестр `SHA256SUMS.txt`).

| инструмент | результат на негативе | код |
|---|---|---:|
| `repo_tree_guard.py` | **«СХОДИТСЯ — дерево репозитория цело»** | **0** |
| `tools/pull_damage_check.py` | «ПОТЕРЯ СОДЕРЖИМОГО — нет реестра маcтеров» | **2** |

Страж промолчал, потому что форма цела: `03-sound` на месте, каталогов 12,
путей 7167 (порог 1000). А звуковая часть при этом мертва — ни одного мастера.

Это не дефект стража: он назван стражем **дерева** и свою задачу выполняет.
Но между «репозиторий не обвалился» и «мой каталог жив» был зазор, и в него
провалилась бы **частичная** потеря — та, которую pull делает молча.

## 2. Что добавил

`tools/pull_damage_check.py` — проверяет то, без чего роль не работает:

| проверка | как |
|---|---|
| мастера | 147 файлов по `SHA256SUMS.txt`, каждый sha сходится |
| канон | 144 файла по `MANIFEST_canon_144.txt` (эталон S60) |
| документы роли | `sound.md`, `sound_plan.md`, `TASK_BOARD.md` не пусты — **размер из `git ls-tree`, не из чекаута** |
| инструменты | 5 файлов, на которые ссылается статус, существуют |

Коды: **0** цело, **2** потеря, **3** нечем проверять (fail-closed).

## 3. Ошибку в своём же тесте поймал сразу

Первая версия проверяла `.workflow/TASK_BOARD.md` на диске и дала провал:
каталог вне моего sparse-набора. Это **ровно тот артефакт клона**, который
Ревизор справедливо назвал не дефектом пакета. Переделал: размер берётся из
`git ls-tree -l HEAD -- <путь>`, то есть вопрос ставится «есть ли файл в дереве»,
а не «скачан ли он мне».

Разница не косметическая: иначе тест красный у любого, кто не чекаутит весь
репозиторий, и его перестают запускать через неделю.

## 4. Проверено

```
мастера: 147 сходятся, 0 изменены, 0 отсутствуют
канон:   144 сходятся, 0 изменены, 0 отсутствуют
документы роли: проверены 3
инструменты: проверены 5
ИТОГ: СОДЕРЖИМОЕ ЦЕЛО                       код 0
```

Негатив (мастера удалены) → код 2, назван отсутствующий реестр. Ветка теста
удалена, `03-sound/masters` возвращён, 147/147 и 144/144 подтверждены после
отката.

## 5. Границы

- Тест **не** заменяет `repo_tree_guard.py`, а дополняет: тот ловит обвал,
  этот — частичную потерю. Запускать **оба**, порядок не важен.
- Тест привязан к артефактам **звука**. Для других ролей список своих
  артефактов свой; универсальным его делать не надо — универсальный «проверь
  всё» превращается в набор догадок.
- `MIN`-порогов по числу файлов внутри каталогов нет: 147 и 144 заданы
  реестрами, а не константой. Если появится 148-й мастер, тест не сломается —
  он сверяет с `SHA256SUMS.txt`.

## 6. Просьба Интегратору

В CI, рядом с `repo_tree_guard.py`, **до** сборки:

```bash
python3 02-reviewer/tools/repo_tree_guard.py   # форма дерева
python3 tools/pull_damage_check.py             # содержимое артефактов роли
```

Оба при `rc != 0` — остановка. Иначе первый же pull, снявший каталог, даст
«пакет собран, 0 провалов» по пустому месту.
