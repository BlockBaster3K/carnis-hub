# Релиз 3.8.0 по команде: тег на `26edbeef` поставлен, asset ZIP не загрузился

**Дата:** 2026-11-27 · **Команда:** тег `v3.8.0` → Release на SHA `26edbeef…` с asset ZIP
· **Итог:** шаги 1, 2, 4 выполнены; шаг 3 (asset ZIP) **заблокирован сетью**

## 1. Уточнение по команде — это было важное расхождение

`26edbeef…` — **не SHA коммита**, а **sha256 пакета**:
`26edbeefa9dc40fcaf29d0d32b2dd65483678d8fb0fc7577f656af13886ea07c`
(16 994 843 Б, 1037 файлов).

Коммита `26edbeef` в репозитории нет ни в одной ветке (`git cat-file -t` → нет).
Если бы я ставил тег на несуществующий объект, Git бы отказал.

Коммит, в котором лежит этот пакет: **`b91153c`** — «rebuild 3.7.3 and 3.8.0
sound packages». Проверено `git cat-file -p b91153c:…zip | sha256sum` →
`26edbeef…`, совпало.

## 2. Что было до меня

Тег `v3.8.0` **уже существовал** — на `4e66645d`, коммите бота
`github-actions` («build: carnis-3.8.0.jar … run 45857171374»), созданном
2026-11-26 16:20.

В том коммите **ZIP вообще нет** — только jar. То есть тег указывал на
коммит сборки, а не на коммит с пакетом. Команда исправляет именно это.

Релиз `Carnis 3.8.0` тоже существовал, с одним asset'ом `carnis-3.8.0.jar`
(17 207 692 Б).

## 4. Почему asset не залился — это сеть, а не права

```
$ curl -o /dev/null -w '%{http_code}' https://uploads.github.com
000                                    ← соединение не устанавливается
$ curl … https://api.github.com  →  200
$ curl … https://github.com      →  200
```

GitHub принимает asset'ы **только** через `uploads.github.com`. Этот хост
отдаёт `SSL_ERROR_SYSCALL` / EOF — три попытки `gh release upload` подряд
дали одинаковый EOF, и прямой `curl` на `upload_url` — тоже.

В песочнице разрешены `github.com`, `api.github.com`,
`codeload.github.com`, `registry.npmjs.org`, `pypi.org`,
`files.pythonhosted.org`. `uploads.github.com` в список не входит.

**Это не «не получилось попробовать».** Я попробовал тремя способами:
`gh release upload`, повтор с задержкой, прямой `curl` на `upload_url` из
API. Отказ один и тот же, на уровне TLS-соединения.

Любое из:

1. **дать сети доступ к `uploads.github.com`** — и я повторю `gh release upload`
   (команда готова);
2. **дозалить вручную** из браузера: Releases → `v3.8.0` → Edit →

## 6. Отдельно: jar в релизе — от СТАРОГО пакета

Реального дефекта не было в задании, но я его вижу и не могу промолчать.

Релизный `carnis-3.8.0.jar` собран прогоном `45857171374` из коммита
**`a1cc56e`**, где пакет был `e08c9b13…` — то есть **до** перерисовки звука
Звуком. Между `a1cc56e` и `b91153c` изменены **6 `.ogg`**:

```
combat_flesh_hit_01/02/03.ogg    (crest 18.0 ± 0.3, правка Ревизора r29)
hive_spread_01_creep / _02_pulse / _03_swell.ogg
```

**Значит: тег указывает на верные байты, но jar в релизе играет прежний
звук.** Тот самый `combat.flesh_hit`, ради которого Звук перерисовывал crest.

Пересборка jar — отдельная команда Архитектора (I7: «не собирать `.jar` без
отдельной команды»), я её не делаю сам. Но при релизе это стоит знать:
если jar должен соответствовать пакету `26edbeef`, нужна пересборка из
`b91153c`.
