## D-001 · Ноги паука стоят вверх дном

**Приоритет:** P2 (визуальный, играть не мешает)
**Фото:** первое
**Симптом:** у заражённого паука ноги направлены вверх, конечности вывернуты.

### Что найдено

Моделей паука в пакете две, и они **из разных конструкций**:

| Файл | Костей | Ног | Состояние |
|---|---|---|---|
| `infected_spider.geo.json` (вариант A) | 24 | 16 | ноги с кубами, обычный паук |
| `infected_spider_b.geo.json` (вариант B) | 28 | 8 | **у `leg_front_left` и `leg_front_right` пустой список кубов** |

В варианте B передние ноги объявлены как кости **без геометрии** (`cubes: []`) —
у них есть только точка вращения и поворот `[0, -12, 8]`. Вместо них стоят
отдельные кости `crusher_femur_*` и `shield_crusher_*`. То есть это не «паук с
ногами наоборот», а **другое существо** — с хвостом, жалом и мандибулами, у
которого часть ног осталась без модели.

### Что надо решить (не техническое, а по концепту)

1. Если вариант B задуман как «Crusher» — дорисовать геометрию передних ног и
   убрать пустые кости.
2. Если вариант B должен выглядеть как паук — заменить модель на корректный
   скелет (8 ног с кубами, как в A).

**Ждём решения:** какая из двух трактовок верна.

## D-002 · Не спавнится вторая вариация заражённых

**Приоритет:** P1 (половина нового контента недоступна)
**Симптом:** при `/summon` и из яйца призыва появляется только одна вариация,
вторая не появляется никогда.

### Причина найдена — порядок инициализации

Во всех четырёх классах (`InfectedZombieEntity`, `InfectedSkeletonEntity`,
`InfectedCreeperEntity`, `InfectedSpiderEntity`) выбор варианта стоит
**в конструкторе**:

```java
public InfectedZombieEntity(EntityType<? extends Monster> type, Level level) {
    super(type, level);
    setCombatVariant(InfectedVariant.random(random));   // ← здесь
}
```

а `setCombatVariant` пишет в синхронизируемые данные:

```java
public void setCombatVariant(InfectedVariant variant) {
    entityData.set(COMBAT_VARIANT, variant.id());
    ...
}
```

Ключевое: `entityData` (`SynchedEntityData`) в ванильном Minecraft создаётся
**не в конструкторе `Entity`, а раньше** — в фабричном методе
`EntityType.create(...)`, который **сразу после** конструктора вызывает
`defineSynchedData()`. Поэтому вызов `entityData.set(...)` из конструктора
идёт до того, как `defineSynchedData()` объявил параметр `COMBAT_VARIANT`.
Изменение уходит в «пустоту», и параметр остаётся значением по умолчанию —
`InfectedVariant.A.id()` (ноль). Отсюда 100% вариант A.

Дополнительно: `applyVariantAttributes(...)` вызывается из конструктора, где
атрибуты ещё не применены — модификаторы тоже теряются.

### Почему это не поймали раньше

Валидатор в CI проверяет геометрию, текстуры и анимации, но **не запускает
игру**. Ошибка проявляется только в рантайме.

### Что надо сделать

Выбор варианта перенести в `finalizeSpawn(...)` — он вызывается после
`defineSynchedData()` и для `/summon`, и для яиц призыва:

```java
if (tag == null || !tag.contains(InfectedVariant.NBT_KEY)) {
    setCombatVariant(InfectedVariant.random(random));
}
```
(перед `applyVariantAttributes`, чтобы не затереть сохранённый вариант).

## D-003 · В пакете остались старые модели заражённых

**Приоритет:** P2 (мусор в jar, путаница при правках)
**Фото:** второе
**Симптом:** старые модели заражённых (например зомби) остались в файлах.

### Что найдено

В 3.8.1 для каждого заражённого лежат **две** модели: базовая и `_b`. Базовая
нигде не удалена и грузится для варианта A. При этом файлы `_b` содержат
**внутри копии анимаций базовой сущности**:

| Файл `_b` | Своих анимаций (`_b.`) | Чужих (базовых) |
|---|---|---|
| `infected_zombie_b` | 8 | 7 |
| `infected_skeleton_b` | 11 | 6 |
| `infected_spider_b` | 7 | 6 |
| `infected_creeper_b` | 14 | 10 |

То есть это не «забытый файл», а **две параллельные ветки арта**, и вторая
частично копирует первую.

### Что надо решить

Нужно ваше решение: какой арт считается актуальным.
- Если актуален `_b` — базовая модель удаляется, `_b` переименовывается в базовую.
- Если актуальна базовая — `_b` удаляется вместе с копиями анимаций внутри.

**Важно:** удалять нельзя, пока не решён D-002 — иначе сломается грузинг
ресурсов по `isVariantA()`.

## D-004 · `carnis_web` и `carnis_spore` без названий, текстур и описаний

**Приоритет:** P2
**Симптом:** во вкладке два предмета с техническими именами, без иконок, без
подсказок.

### Что это вообще такое

- **`carnis_web`** (`BlockItem` для `CarnisWebBlock`) — та самая временная
  паутина, которую оставляет паук варианта B после прыжка. Ставится как блок,
  сама исчезает через 160 тиков.
- **`carnis_spore`** (`Item`, стак 16) — боеприпас для `CarnisSporeBombEntity`,
  то есть «споровая бомба». Выдаётся как предмет-снаряд.

Оба предмета **зарегистрированы намеренно** и добавлены во вкладку мода
(`ModCreativeTabs`, строки 59–60) — это не случайный мусор, а забытое
оформление.

### Чего именно не хватает

| Чего нет | Подтверждение |
|---|---|
| Названия | в `en_us.json` нет ключей `block.carnis.carnis_web`, `item.carnis.carnis_spore` |
| Модели предмета | нет `models/item/carnis_web.json`, `models/item/carnis_spore.json` — подтверждено логом |
| Блока | нет `blockstates/carnis_web.json`, нет текстуры `textures/block/carnis_web.png` |
| Подсказки | нет `tooltip.carnis.*` для обоих |

### Цитата из лога

```

  'carnis:blockstates/carnis_web.json' missing model for variant: 'carnis:carnis_web#'
[Worker-Main-3/WARN]: Unable to load model: 'carnis:carnis_web#inventory'
```

## D-005 · Заражённые светятся, тени не рендерятся

**Приоритет:** P1 (портит вид всех новых мобов; заметно и днём, и ночью)
**Фото:** третье
**Симптом:** модели заражённых словно светятся изнутри, во тьме видны как днём,
тени на них не ложатся.

### Причина найдена — `AutoGlowingGeoLayer` вырезает тело

Все рендереры заражённых добавляют светящийся слой:

```java
addRenderLayer(new OptionalGlowLayer<>(this));   // zombie, skeleton, creeper
addRenderLayer(new AutoGlowingGeoLayer<>(this)); // spider
```

`OptionalGlowLayer` — наследник `AutoGlowingGeoLayer`, он лишь проверяет наличие
файла маски. Сама логика в GeckoLib 4.8.4, файл
`software/bernie/geckolib/cache/texture/AutoGlowingTexture.java`:

1. Берётся основная текстура и маска `<имя>_glowmask.png`.
2. `GeoGlowingTextureMeta.createImageMask()` проходит **только по пикселям
   маски** и для каждого делает:
   - в маске: переносит цвет из основной текстуры → это и есть «светящаяся» часть;
   - **в основной текстуре: затирает пиксель в ноль**.
3. Итог: базовый слой рисует **только то, что НЕ попало в маску**, а маска
   рисуется вторым проходом при `LightTexture.FULL_SKY` (максимальный свет).

Замер по реальным файлам 3.8.1 — сколько тела вырезается из базового слоя:

| Текстура | Пикселей тела | Вырезано маской | Осталось |
|---|---|---|---|
| `infected_zombie` | 4096 | 4032 | 64 (2%) |
| `infected_zombie_b` | 2490 | 2367 | 123 (5%) |
| `infected_skeleton` | 2048 | 2020 | 28 (1%) |
| `infected_skeleton_b` | 2004 | 1860 | 144 (7%) |
| `infected_spider_b` | 3396 | 3140 | 256 (8%) |
| `infected_creeper_b` | 3456 | 3328 | 128 (4%) |
| `infected_cave_spider` | 2048 | 2000 | 48 (2%) |

**92–99% тела вырезается** и показывается заново при полном свете. Поэтому моб
не затемняется, не получает теней — светится почти весь. Это не «слишком
яркий glowmask», а **инвертированная семантика маски**.

### Что надо сделать

Маска должна содержать **только те пиксели, которые реально светятся** (глаза,
раны, прожилки), а остальное — прозрачным. Сейчас она покрывает почти всё тело.
Проверка обратная: доля вырезанного тела должна быть 5–15%, а не 92–99%.

## D-006 · Высокая скорость и рассинхрон анимации ходьбы

**Приоритет:** P1 (ломает ощущение от всех новых мобов)
**Симптом:** заражённые бегают быстрее, чем положено; анимация шага «не
поспевает» — моб делает шаг и уже прошёл 10 блоков.

### Две отдельные причины

**1. Скорость в целях ИИ выше ванильной.**

| Цель | Множитель | Против ванильного |
|---|---|---|
| `VariantMeleeAttackGoal` | **1.3** | 1.0 у `MeleeAttackGoal` |
| `InfectedSkeletonSniperGoal` | **1.15** | 1.0 |
| `CreeperHornChargeGoal` | 1.0 | норма |
| `ZombieScytheCleaveGoal` | 1.0 | норма |

Базовые атрибуты в порядке: зомби `0.25`, скелет `0.27`, паук `Spider` +
20 HP, крипер `Creeper` + 24 HP. То есть «быстро» даёт не атрибут, а **множитель
навигации 1.3** у зомби в бою.

**2. Анимация ходьбы не привязана к реальной скорости.**

Контроллер движения:

```java
return state.setAndContinue(state.isMoving() ? WALK : IDLE);
```

`isMoving()` — это «двигается / не двигается», а не «как быстро». Анимация
крутится с фиксированной скоростью 1 цикл, независимо от того, прошёл моб 1
блок или 10. Отсюда ощущение «схалтуренной» ходьбы.

Плюс: `WALK` — это **всегда базовая** анимация, даже для варианта B:
```java
private static final RawAnimation WALK = RawAnimation.begin().thenLoop("animation.infected_zombie.walk");
```
Тогда как для ассимиляции и пульса вариант B выбирается явно (`ASSIMILATE_B`,
`PULSE_B`). То есть у варианта B ходьба играет от модели A — ещё одна причина
«шаг не тот».

Длины циклов ходьбы: зомби A `1.2 с`, зомби B `1.0 с`, паук A `1.0 с`,
паук B `1.0 с`.

### Что надо сделать

1. `VariantMeleeAttackGoal` → `1.0`; `InfectedSkeletonSniperGoal` → `1.0`.
2. Синхронизировать анимацию со скоростью через
   `state.getController().setAnimationSpeed(...)` от фактической скорости моба
   (или `walkAnimationSpeed`), а не флагом `isMoving()`.
3. Для варианта B использовать свои константы `*_b.walk`, как сделано для
   пульса и ассимиляции.

## D-007 · Заражённый тонет и не выходит из воды

**Приоритет:** P3 (нужно воспроизвести, но симптом опасный — моб умирает)
**Симптом:** зомби погнался за спрутом в воду, медленно плыл, начал задыхаться
и **умер, не пытаясь всплыть**.

### Что найдено

В `HiveEntity` (родитель зомби, скелета, амalgama) **нет ни одного**
переопределения, связанного с водой: ни `canBreatheUnderwater`,
ни `getWaterSlowDown`, ни `canStandOnFluid`. В 3.8.0 их тоже не было — то есть
это не регрессия, а изначально отсутствующее поведение.

Причина того, что моб **выбрал** водную цель, видна в `CarnisHuntPreyGoal`:

```java
public static boolean isPrey(LivingEntity target) {
    if (!(target instanceof Mob) || target instanceof HivemindLinkedMob || target instanceof Player) return false;
    ResourceLocation id = ForgeRegistries.ENTITY_TYPES.getKey(target.getType());
    return id != null && "minecraft".equals(id.getNamespace());
}
```

Любой ванильный моб — добыча. Спрут подходит по всем условиям, проверки «а не
в воде ли цель» нет. Дальше ванильная навигация пытается идти в воду, а
утопление никто не отменяет.

### Чего не хватает для точного диагноза

Нужно воспроизвести в тестовом мире и подтвердить:
- тонет ли только зомби или все заражённые;
- тонет ли в **воде** или в **tainted sludge** (жидкость мода);
- прекращает ли он преследование, если цель под водой.

Предварительно: причина не в коде воды, а в **отсутствии инстинкта
самосохранения** — нет ни всплытия, ни отказа от водной цели.

## D-008 · Краш при установке `nerve_pillar` — P0

**Приоритет:** P0 (краш; блок нельзя ставить вообще)
**Симптом:** при попытке поставить `nerve_pillar` игра падает.

### ⚠️ Стектрейса в присланном логе нет

В `latest.log` **нет записи о краше**. Файл обрывается на строке 13:41 и
заканчивается предупреждениями об анимации текстуры:

```
[13:41:26] [Render thread/WARN]: Invalid frame index on sprite carnis:textures/block/nerve_pillar.png frame 1: 1
...
[13:41:26] [Render thread/WARN]: Unused frames in sprite carnis:textures/block/nerve_pillar.png: [2, 1, 3]
```

Это **не стектрейс**, а предупреждения рендера. При этом они появляются
буквально в момент работы с блоком, поэтому записаны как **сильный подозреваемый**,
а не как доказанная причина.

### Подозреваемый №1 — битый `.mcmeta`

Файл `assets/carnis/textures/block/nerve_pillar.png.mcmeta`:

```json
{"animation": {"frametime": 6, "frames": [0, 1, 2, 3, 2, 1]}}
```

Он объявляет **6 кадров** (индексы 0–3). Но `nerve_pillar.png` — это
**одно изображение 64×64**, то есть в нём **ровно 1 кадр**. Отсюда ровно те
сообщения: «Invalid frame index … frame 1: 1», «Unused frames … [2, 1, 3]».

Отдельно лежат `nerve_pillar_0.png` … `nerve_pillar_3.png` (по 64×64) — похоже,
задумывалась анимация из отдельных файлов, но формат `.mcmeta` так не работает:
он режет **один** вертикальный лист.

### Что нужно сделать в первую очередь

**Прислать файл из `.minecraft/crash-reports/`** (или `latest.log` того
запуска, где реально был краш). Без стектрейса можно только гадать, и есть риск
починить не то.

Приоритетный порядок разбора, когда стектрейс будет:
1. `NervePillarBlock.onPlace` → `CarnisWorldData.halveRemainingShock(...)`
2. `HiveNetwork.observe(...)` в `onPlace` и `randomTick`
3. `NervePillarBlockEntity.serverTick` — приведение `(ServerLevel) level`
   в `spawnAuraParticles`
4. Рендер `NervePillarRenderer` / `NervePillarModel`

## Чего в реестре ещё нет

Проверено по вашим отчётам, но **не воспроизведено** — при следующих прогонах
обратить внимание:

- `Loaded 7 recipes` при 41 файле рецептов. **Проверил пакет: все 41 рецепт
  валидны** (21 shapeless, 19 shaped, 1 smelting), ссылок на несуществующие
  предметы нет. Значит дело не в данных, а в том, что Forge считает только
  часть — вероятно, остальные уходят в датаген/Smithing и грузятся отдельной
  фазой. Нужна проверка в JEI: находятся ли рецепты кос и брони поиском.
- Эффекты `paralysis` и `vulnerability` без названий (нет ключей в `en_us.json`).
  Косметика, но в реестр не внесена — ждёт подтверждения, что это не задумано.
- Отсутствие перевода на русский: весь интерфейс на английском, хотя в игре
  язык русский (видно по чату).
