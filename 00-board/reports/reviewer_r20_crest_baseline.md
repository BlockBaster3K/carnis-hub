# Ревизор · R20: эталонная таблица crest (З-29) — пересчитал сам, две находки

**Дата:** 2026-11-27 · **Артефакт:** `00-board/reports/sound_crest_baseline.md` (S28) · **Инструмент:** `02-reviewer/tools/crest_delta.py` (получил режим `--table`)

## 1. Что проверял и как

Разобрал таблицу машинно (не глазами) и пересчитал по её же числам обе формулы — это и есть «пересчитать самому, а не поверить отчёту».

| Утверждение Звука (S28) | Мой пересчёт |
|---|---|
| строк **276** (144 канона + 132 в `sounds_380`) | **276** |
| стационарных / транзиентных **50 / 226** | **50 / 226** (17+33 / 127+99) |
| формула З-29 с `min()` → **44 вне допуска** | **44**, из них **37 стационарных** — ровно как заявлено |
| формула `max(порог; baseline+0,05)` → **0 вне** | **0** |
| колонка «допуск» = `max(порог; baseline+0,05)` | **276/276** (различия только от округления до 0,01) |
| канон: baseline медиана, максимум | медиана **0,102**, максимум **2,293** дБ |
| `sounds_380`: медиана, максимум | медиана **0,054**, максимум **0,373** дБ |

**Вывод по формуле подтверждаю:** с `min()` допуск никогда не превышает порог типа (у стационарных это 0,05), поэтому baseline не влияет вообще, и норма валит 44 принятых файла без всякой правки. Формула Звука `max(порог_типа; baseline + 0,05)` — рабочая. Это не «предложение роли», а исправление решения Архитектора, и Архитектор его уже принял (З-29 в доске с `min()`).

## 2. Находка 1 (важная): колонка «фактический Δcrest» равна baseline во **всех 276** строках

Проверил построчно: `|Δcrest − baseline| < 1e-9` **у всех 276**. Это значит, что в таблице лежит **шум файла против его же перекода**, а не сравнение сданного файла с оригиналом. Следствия:

1. Строка отчёта «**вне допуска 0**» — **тавтология**: файл всегда проходит допуск, построенный из его собственного шума. Как доказательство она не значит ничего.
2. Таблицу **нельзя** читать как «вердикт по банку». Её годная часть — **допуск per-file** (и тип сигнала); сам вердикт обязан считаться в гейте по сданному файлу и **round-trip-эталону оригинала**.
3. Для 132 файлов `sounds_380` оригиналов нет вовсе — там «Δcrest = baseline» единственное, что вообще можно измерить. То есть для них норма принципиально проверяет только «файл не перерисован относительно своей же трубы» — и это надо честно назвать, а не выдавать за проверку.

## 3. Находка 2 (важная): crest почти не ловит изменение тембра — п.4 З-29 неверен

З-29 п.4 требует: «файл с изменённым тембром обязан превышать свой допуск; негативный тест обязателен и **достаточен**». Измерил огибающую чувствительности: взял файл, применил правку **только тембра** (RMS возвращён к исходному), перекодировал, сравнил crest с round-trip-эталоном.

| Правка тембра | Стационарный (допуск ≈ 0,20) | Транзиентный (допуск 0,60) |
|---|---:|---:|
| полка ВЧ +6 дБ от 4 кГц | **0,91 — поймано** | 0,18 — **пропущено** |
| срез НЧ −6 дБ ниже 500 Гц | **0,00 — пропущено** | **0,85 — поймано** |
| ФНЧ 6 кГц (глухой звук) | 0,46 — поймано | **0,07 — пропущено** |
| вырез середины −12 дБ на 1 кГц | 0,67 — поймано | 2,23 — поймано |
| перегруз `tanh×3` | 0,63 — поймано | 6,28 — поймано |

Половина реалистичных правок тембра (глухой ФНЧ у ваншота, срез низа у эмбиента, полка ВЧ у удара) проходит **вне** нормы. Причина в природе величины: crest = peak/RMS, он меряет **динамику**, а не окраску — и по определению слеп к спектральным сдвигам, не меняющим пик.

**Что это значит практически:** crest-норма — правильная проверка **против лимитера/перекодирования** (это была цель З-21), но **не** проверка тембра. Требование п.4 «тест достаточен» надо переписать: тембр проверяет `tools/timbre_check.py` (центр + полосы), который в гейте уже есть и который такие правки видит по построению. Иначе получается проверка, которую легко обойти самой безобидной эквализацией.
