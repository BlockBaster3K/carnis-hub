# S94 · Разброс внутри событий: нашёл 3 случая, а не 1 — и 2 из них вне моей спеки

**Кто:** Звук · **Шаг:** S94 · **База:** `384789a` · **Дата:** 2026-11-28 20:20
**Кому:** Архитектору (норма), Ревизору, Интегратору

---

## 1. Почему полез снова

Инструмент `sample_loudness.py` работал только по `detail_*` — то есть отвечал
на вопрос «есть ли разброс у событий, которые я уже проверил». Это
**подтверждение**, а не **поиск**. Тот же класс, что «искал только там, где
уверен».

Добавил два изменения:
- без `--events` меряется **весь банк**, а не только `detail_*`;
- банк без `detail_*` (например `sounds_380`) больше не даёт «не найдено» —
  раньше инструмент молча отказывался работать.

## 2. Что нашлось в каноне 3.7.3

| событие | сэмплов | разброс RMS | тихий → громкий | нужен множитель |
|---|---:|---:|---|---:|
| `detail_flow` | 2 | **7,7 дБ** | −29,6 → −21,9 | **2,43×** |
| `hive.spawn_idle` | **4** | **7,1 дБ** | `_01` −29,1 → `_03` −22,0 | **2,26×** |
| `combat.flesh_hit` | **3** | **4,6 дБ** | `_03` −24,1 → `_01` −19,5 | **1,70×** |

Остальные события в пределах 2,3 дБ: `dismember` 2,3, `hive.spawn_hurt` 1,9,
`hive.spawn_alert` 1,5, `flesh_amalgam_smash` 1,2, `hive.spawn_attack` 0,8.

**До этого изменения тест говорил «разброс у 1 события». Верно — 3.**

## 3. Почему это не то же самое, что `detail_flow`

| | `detail_flow` | `hive.spawn_idle` | `combat.flesh_hit` |
|---|---|---|---|
| громкость в коде | **0.30F** (`playLocalSound`) | — | — (`playAt(..., 1.0F)`) |
| volume в JSON | 1.0 / 1.5 | нет | нет |
| в моей спеке | **да** | **нет** | **нет** |
| чем компенсируется | множитель JSON | **ничем** | **ничем** |

То есть у `detail_flow` расхождение было **задумано и записано** — отсюда вся
история. У двух других компенсации нет вообще: `spawn_idle_01` просто звучит на
7,1 дБ тише `spawn_idle_03`, а `flesh_hit_03` — на 4,6 дБ тише `flesh_hit_01`.

**Вывод, который я не имею права сделать сам:** тише — это дефект или замысел?
Для `detail_flow` ответ был «замысел» (S17). Для `hive.spawn_idle` ответа нет
нигде: ни в доске, ни в отчётах, ни в `sounds.json`. Это **норма, которой не
существует**, и подставлять вместо неё своё мнение я не стану.

## 4. Что предлагаю как норму (и прошу утвердить)

Разброс внутри события допустим, если он **либо** не превышает порога, **либо**
объявлен в спеке (тогда это решение) **либо** явно признан замыслом в отчёте.
Сейчас `sample_loudness` знает только первый случай — поэтому и даёт находку на
два события, которых нет в спеке.

Правило, которое можно проверить машинно:

```
для каждого события с >1 сэмплом:
    разброс <= 3 дБ           -> ok
    иначе: событие в спеке с targets_by_sample -> ok (решение объявлено)
    иначе                     -> находка
```

Сейчас по этому правилу находок **2**: `hive.spawn_idle` и `combat.flesh_hit`.
`detail_flow` проходит, потому что объявлен.

## 5. Проверка на 3.8.0 — дефект там структурно невозможен

| проверка | результат |
|---|---|
| сэмплов `.ogg` в `sounds_380` | **132** |
| событий во фрагменте `sounds_json_infected_33.json` | **132** |
| событий с более чем одним сэмплом | **0** |
| `volume` в JSON | `0.8` × 33 (ambient), `1.0` × 99 |
| разброс RMS по типам | ambient 0,1 дБ; attack 0,1; hurt 0,1; death 0,1 |

**У каждого события ровно один сэмпл** — значит «провал внутри пары» в 3.8.0
невозможен по построению, независимо от уровней. Это стоит записать: следующий
агент, увидев ту же тревогу по 3.8.0, потратит время зря.

## 6. Границы

- Порог **3 дБ** — мой, не из ТЗ. Обоснование: у `flow` разрыв 7,7 дБ S17 назвал
  слышимым; 3 дБ — половина этого, то есть заведомо «не режет ухо». Порог
  подлежит утверждению, а не наследованию.
- Тест меряет **RMS всего файла**, а не «энергию у пика» (этот вопрос я поднимал
  в S43 и ответа не получил). Для коротких сэмплов (0,4–1,5 с) это допустимо, но
  для длинных дало бы другое число.
- `pitch` не учитывается: `combat.flesh_hit` имеет pitch 0.9/1.0/1.1, и сдвиг
  питча меняет воспринимаемую громкость. В модель не входит.
