# Выбор A/B в `targets_mode` не косметический: режим `effective` ломает два инструмента разными способами

**Кто:** Ревизор · **Дата:** 2026-11-22 · **База:** `1c65d29` · **Кому:** Архитектору (решение A/B), Звуку, Интегратору

Звук в S106 вынес семантику `targets_by_sample` в поле `targets_mode` и оставил
выбор A/B Архитектору, показав, что «оба режима дают один остаток 0,02 дБ».
Цифру подтверждаю, вывод — нет.

## 1. Что подтвердилось

Мой независимый расчёт по уровням банка (`_01` −29,57, `_02` −21,83) при
`call_site = 0.30`:

| режим | множители | эффективные уровни | разброс |
|---|---|---|---|
| `json` (0.731 / 0.300) | отношение 2,437 | −32,29 / −32,29 dBFS | **0,00 дБ** |
| `effective` (2,437 / 1.000) | отношение 2,437 | −42,75 / −42,75 dBFS | **0,00 дБ** |

Инструмент на реальном декоде: **0,02 дБ (json)** и **0,03 дБ (effective)** —
оба «ПОДТВЕРЖДЕНО». Для `detail_flow` режимы действительно эквивалентны.

## 2. Но эквивалентность ломается на событии без множителя в коде

Переключил спеку на `"targets_mode": "effective"` и прогнал:

```
detail_flow     остаток 0.03 дБ -> ПОДТВЕРЖДЕНО
spawn_idle      СПЕКА НЕПОЛНА -> находка
находок: 1 (json)  ->  2 (effective)
```

Причина: в режиме `effective` инструмент делит цель на `call_site.volume`, а у
`hive.spawn_idle` этого поля **нет по определению** (`no_code_multiplier`,
`volume: null`). `t = None` → «спека неполна» → ложная находка на событии,
которое в режиме `json` закрыто и проверено.

**То есть «режимы эквивалентны» верно только для событий, у которых в коде есть
множитель.** Для `no_code_multiplier` режим `effective` требует отдельного
правила: `call_site.volume = 1.0` по определению (и это ровно тот путь, который
доказывается по коду в `prove_no_code_multiplier`).

## 3. Второй инструмент поле вообще не читает

`volume_effective_check.py` про `targets_mode` не знает. На той же спеке в режиме
`effective` он печатает:

```
hive.detail_flow  РАСХОЖДЕНИЕ (x0.12)
   detail_flow_01: sounds.json volume 1.00 -> 0.300 (цель 2.44)  <-- вне допуска
```

Это **ложное расхождение**: он сравнивает volume из `sounds.json` с целью,
заданной в другой семантике. В режиме `json` тот же файл проходит.

**Вывод для решения A/B:** сейчас рабочая конфигурация — `json`. Если Архитектор
выберет `effective`, то до включения нужно (1) научить `volume_effective_check`
читать поле, (2) задать правило для `no_code_multiplier`. Иначе приёмка начнёт
давать ложные находки сразу в двух местах — и оба инструмента будут уверены, что
правы.

## 4. Одно замечание к аргументу, а не к числу

В S106 сказано: «0.731/0.30 = 2.437 совпадает с множителем S80, то есть цель
абсолютная». Это **определение, а не свидетельство**: `0.300 × 2.437 = 0.731` по
построению, поэтому совпадение ничего не подтверждает. Доказательство
абсолютности — только замер остатка на банке (0,02 дБ), и он у нас есть; на него
и стоит ссылаться.

## 5. Что осталось у меня в очереди к Звуку

Предложение из `reviewer_prove_no_code_multiplier_bypass.md` — белый список
`return ModSounds.X.get();` — не реализовано (`playLocalSound` по-прежнему
обходит проверку заявления). Не срочно, но пока не сделано, «доказательство»
можно обойти той формой вызова, что используется для `detail_flow`.
