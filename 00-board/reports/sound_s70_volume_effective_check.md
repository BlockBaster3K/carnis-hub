# S70 · Итоговая громкость считается машиной, а не глазами

## 1. Зачем — после того, как я ошибся в S62

В S62 я сравнил ТЗ громкостей T-3202 с `sounds.json`, получил «7 из 9 не по ТЗ»
и ошибся: множителей **два**, они перемножаются. Ошибка была не в арифметике, а в
**методе**: я сравнил норму с одним из двух входов и не имел инструмента, который
сказал бы «ты смотришь не на то».

Значит лечить надо метод: инструмент, который считает итог и умеет ответить
«это не норма», а не только «файл X отличается от файла Y».

## 2. Что сделал

`tools/volume_effective_check.py` + `03-sound/spec/volume_spec_t3202.json`.

```
effective = call_site_volume (Java) * volume каждого сэмпла (sounds.json)
```

| решение | почему так |
|---|---|
| норма — во **входном JSON**, а не в коде теста | урок S54/S56: второе определение нормы в двух местах |
| путь к Java **из спеки**, не поиск по дереву | поиск нашёл бы вызов в любом файле и дал ложное «ok» |
| для вызова через переменную — `arg_marker` **с проверкой**, что событие выбирается в том же файле | иначе маркер — допущение, а не факт кода |
| `tolerance` во входе (0.005) | допуск — часть нормы, не константа в коде |

## 4. Негативы — шесть, и важен третий

| сценарий | код | что напечатал |
|---|---:|---|
| пакет не найден | **3** | `ОШИБКА: .../sounds.json` |
| спека не читается | **3** | `ОШИБКА` |
| **починка `volume 1.5 → 1.0`** | **0** | **«9 из 9 в норме»** |
| ошибка S62: `0.30` в JSON поверх call-site `0.30F` | **2** | `0.090` — **×0.30**, втрое тише |
| событие удалено из `sounds.json` | **3** | `'synapse_shock'` |
| call-site понижен до `0.1F` | **2** | `0.100` — ×0.12 |

Третий важен больше остальных: он **проверяет рекомендацию**, которую я дал в S68.
Не «я думаю, что 1.5→1.0 починит», а «после 1.5→1.0 тест даёт 9 из 9». Четвёртый
показывает цену моей прежней ошибки числом: **0.09 вместо 0.30**.

## 5. Границы

- Тест **не в гейте** — `tools/` не моя зона. Прошу Интегратора: вызов на каждый
  пакет, при `rc != 0` — fail. Сигнатура: `--pkg <каталог версии> --spec <json>`.
- Спека **не** выведена из кода: цели взяты из ТЗ доски. Если ТЗ изменится, править
  JSON, а не тест — это и есть смысл выноса нормы из кода.
- Проверяются **только 9 событий T-3202**. Остальные 134 записи `sounds.json` не
  охвачены, потому что ТЗ на них нет. Когда появится — расширяется спека, код не
  меняется.
- `arg_marker` остаётся слабым местом: пять detail-событий идут через общий вызов
  `playLocalSound(..., detail, ...)`. Тест требует, чтобы событие выбиралось в том
  же файле, но **не** доказывает, что выбранный `detail` попадает именно в этот
  аргумент. Это названо, а не спрятано.

## 6. Что остаётся сделать человеком

Одна правка, и она не моя:

```json
"hive.detail_flow": {"sounds": [{"volume": 1.5, "pitch": 0.95}, ...]}
                                   ^^^ 1.0, pitch сохранить
```

Java не трогать. После правки тест должен дать код 0 — и это проверяемо до сборки.
