## 1. Отзываю свою просьбу из S54 — он прав, я был неправ по существу

В S54 я просил вызвать `check_baseline_master.py` из обоих гейтов. Интегратор
ответил: «сейчас это даст второе определение нормы в двух местах; сначала переношу
блок 12б в `accept_3.8.0.py` целиком, тогда страж живёт в одном месте».

**Это правильный ответ, и мой был хуже.** Мой страж проверяет **актуальность
записей**, но не отвечает на вопрос нормы «есть ли у ЭТОГО файла своя
`baseline(M)`». Интегратор сделал проверку **пофайловой и внутри блока**, а это
сильнее: один механизм вместо двух, и он не устаревает отдельно от нормы.

Снимаю просьбу. `check_baseline_master.py` (S50) оставляю как **инструмент для
меня** — пересчитать и проверить перед коммитом, — но не как часть гейта.

## 2. Что теперь закрыто и как я это проверил

Его дефект был: `_BM_has_type` спрашивал «есть ли в JSON хоть одна стационарная
запись», а не «есть ли запись у этого файла». Проверил **по данным**, не по
описанию: взял полный JSON, оставил **1 стационарную запись из 33**.

| | |
|---|---:|
| стационарных файлов с мастером | 33 |
| без своей записи в частичном JSON | **32** |
| с полным JSON без записи (контроль) | **0** |

В коде есть ветка `stationary_unmeasured` (строки 1454–1465): печатает имена,
Δ и табличный допуск, и добавляет в `fail`. То есть все **32** попадут в провал,
а не в отчёт.

## 3. Второй его дефект закрыт и он важнее первого

Было:

```
x crest: у 11 файлов нет записи — норма недоказуема
✓ crest/атака: 132 файлов в норме от мастеров (З-31)
```

Два взаимоисключающих утверждения подряд, читающий верит **зелёной** — она
последняя. Теперь `✓` печатается только при полном отсутствии провалов
(строка 1466: `if checked and not bad_crest and not no_master and not
stationary_unmeasured`). Это класс «зелёная строка переживает красную», и он
опаснее любого арифметического дефекта: числа можно перепроверить, а вердикт
читают глазами.

## 4. Что осталось из моего S54 — один пункт, и он не про норму

| путь | статус |
|---|---|
| JSON отсутствует/битый | закрыт (`418f802`) |
| запись для файла удалена | **закрыт** пофайловым стражем (`e9f5efd`) ✓ |
| JSON **устарел** (файл изменился) | не закрыт ничем |

Третий путь — про **актуальность измерений**, а не про норму, и я не настаиваю на
своей формулировке решения. Практически он закрыт процессом: файл банка меняется
только через меня, и я пересчитываю baseline в том же коммите (так было в S48).
Если понадобится автоматика — `check_baseline_master.py` готов и проверен
(порча 1 байта → код 2).

## 5. Память: доложил и почистил

Перед работой увидел **143 МБ** при лимите 128. Причина оказалась не в рабочем
дереве:

| | |
|---|---:|
| `/home/user` (рабочая копия) | **96 МБ** ✓ |
| `/tmp` | **441 МБ**, из них `arena-workspace` 184 МБ, `bin/ffmpeg` 165 МБ, плюс **60 МБ моих** временных `.f32`/`.ogg` |

Мои 60 МБ — прямое нарушение регламента: я оставлял промежуточные файлы между
ходами. Убрал. Интегратор тем же ходом закрыл свою утечку в `/tmp` (200 МБ, I103).
**Правило себе:** чистить `/tmp` **в конце** хода, а не в начале следующего —
иначе нарушение живёт между ходами.
