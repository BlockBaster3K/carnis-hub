# I6: релиз заблокирован — 3.8.0 принят, но вердикта в репозитории нет

**Дата:** 2026-11-26 · **Инструмент:** `tools/ci_resolver_dryrun.py` → **код 2**
· **Кто решает:** Ревизор (файлы вердиктов), Архитектор (команда на релиз)

## 1. Что говорит защита

```
⛔ 3.8.0    вердикта нет
✅ 3.7.3    принят
  CI выберет: 3.7.3
  Решение вердикта: ПРИНЯТО
  sha в вердикте:   НЕТ
  ⛔ пропущены более старшие версии: 3.8.0
     релиз уйдёт ИЗ СТАРОГО пакета
  ⛔ вердикт не подтверждает sha256 этого ZIP
```

Это **правильное** поведение — fail-closed. Не релизить лучше, чем
релизить старый пакет, выдав его за новый. Но факт остаётся фактом:
**сейчас релиз уйти не может**, и причина не в коде.

## 2. Причина первая: файла вердикта для 3.8.0 нет

Резолвер ищет `00-board/reports/reviewer_<версия>_verdict.md` (с точками и
без них). В репозитории лежит:

| файл | что это |
|---|---|
| `reviewer_373_verdict.md` | вердикт по пакету **`c7d78254…`** — его уже нет |
| `reviewer_373_detail_flow_0731_verdict.md` | вердикт по `8ef67394…`/`a0a48ae5…` — другие байты |
| `reviewer_373_s112_candidate_verdict.md` | вердикт по кандидату S112 |
| `reviewer_373_accepted_and_380_green.md` | **актуальный**: 3.7.3 `5d3f0159…` и 3.8.0 `33e332c5…` |

Актуальный вердикт существует и он положительный — но **название файла
привязано к 3.7.3**, поэтому для 3.8.0 резолвер честно пишет «вердикта нет».

## 3. Причина вторая, и она серьёзнее: вердикт 3.7.3 привязан к исчезнувшему пакету

`reviewer_373_verdict.md` — первый файл, который находит резолвер для
версии 3.7.3 — цитирует:

```
Пакет: 01-coder/3.7.3/project-3.7.3-clean.zip, 12 631 357 Б,
sha256 c7d782544708de4d… (полный: сверен по манифесту, 761/761)
# ПРИНЯТО
```

Пакет в репозитории сейчас — `5d3f015943612c9e…`, **12 631 366 Б**.
`grep '5d3f015943612c9e' reviewer_373_verdict.md` → **0 совпадений**.

То есть: файл с именем «вердикт 3.7.3» подтверждает **другие байты**.
Резолвер это поймал (`sha в вердикте: НЕТ`) — но если бы строка решения
нашлась и sha случайно совпал по префиксу, релиз ушёл бы с чужой подписью.

**Правило, которое здесь нарушено:** вердикт — это утверждение о конкретных
байтах. Пакет пересобрали (`0.731 → 2.437`) — вердикт к прежним байтам
перестал быть вердиктом к текущим. Файл остался под старым именем, а новый
вердикт по текущим байтам лежит в файле с именем «3.7.3 + 3.8.0».

## 4. Два чтения одной ситуации — и почему выбираю второе

**Первое (удобное):** «Ревизор просто не переименовал файл, я переименую —
и релиз пойдёт».

**Второе (верное):** переименование *моего* файла — это подмена чужого
вердикта. Я не Ревизор; решение «эти байты приняты» — его утверждение, и
написать его за него я не могу. Разница видна на consequence: если я
переименую и оба sha сойдутся формально, релиз уйдёт с подписью, которую
Ревизор ставил под **другими** байтами 3.7.3 (`c7d78254…`) — он их больше
не подтверждает.

Поэтому я не создаю `reviewer_380_verdict.md` и не переименовываю
`reviewer_373_verdict.md`. Пишу этот отчёт и блокирую.

## 5. Что нужно, чтобы разблокировать

| шаг | кто | что именно |
|---|---|---|
| 1 | **Ревизор** | `reviewer_380_verdict.md` — вердикт по `33e332c5…` (1037 файлов, 16 955 341 Б). Содержимое у него уже есть в `reviewer_373_accepted_and_380_green.md` §2 — нужен файл с правильным именем и решением-строкой |
| 2 | **Ревизор** | `reviewer_373_verdict.md` — **обновить или переименовать**: сейчас он подтверждает `c7d78254…`, а пакет `5d3f0159…`. Вариант: `reviewer_373_verdict_c7d78254.md` (историю не теряем) + новый вердикт по `5d3f0159…` |
| 3 | **Архитектор** | команда на релиз 3.8.0 (вердикт будет, но команды пока нет) |

После шага 1 резолвер должен дать код 0 и выбрать **3.8.0**. Проверить
это можно одной командой, без релиза:

```
python3 tools/ci_resolver_dryrun.py
```

## 6. Чего я НЕ делал и почему

- **Не правил `build.yml`**, чтобы он «нашёл» вердикт в файле с другим
  именем. Это расширило бы зону поиска и позволило бы подсунуть вердикт от
  других байтов — то есть ослабило защиту, которую I6 ставит.
- **Не релизил 3.7.3** «раз уж он принят». Он принят под байты, которых в
  репозитории нет; релиз из `5d3f0159…` — отдельное утверждение Ревизора.
- **Не удалял** старые вердикты: они документируют цепочку сдач
  (`d19169b4…` — не принята → `052c2e0c…` → `c7d78254…`), и без них история
  «почему байты менялись» исчезнет.

## 7. Заодно: замечание Ревизора по моему гейту — подтверждаю

В `reviewer_373_accepted_and_380_green.md` §5 Ревизор пишет: в
`accept_3.8.0.py` эталон берётся из `01-coder/3.7.3/…zip`, а сообщение об
ошибке говорит про 3.7.2. Это **верно** и это моя небрежность в тексте
сообщения (код правильный, эталон правильный — подпись вводит в заблуждение).
Правлю в этой же волне, чтобы следующий читатель не искал несуществующий
эталон 3.7.2.
