# CI падал на всех версиях: `ls | head` под `pipefail` — найдено и исправлено

**Дата:** 2026-11-25 · **Роль:** Интегратор
**Статус:** ✅ исправлено, первый ЗЕЛЁНЫЙ прогон — `bd31dcd`, workflow_dispatch, success
**Коммит:** `bd31dcd`

## 1. Что было

Шаг **Resolve package** падал на **каждом** коммите, всех ролей, начиная
с первого; аннотация всегда одна: `Process completed with exit code 2`.
Логи через API недоступны (`EOF`), поэтому причину искали по коду.

Первый мой диагноз (`grep -q` под `set -e`) был **неверным** — от него остался
безвредный `|| true`. Настоящая причина другая и объясняет код 2.

## 2. Причина

Actions запускает шаг как `bash --noprofile --norc -eo pipefail`, то есть
**с `pipefail`**. В шаге было:

```bash
VERD2=$(ls -1 00-board/reports/reviewer_*"$VBASE"*_verdict.md \
           00-board/reports/reviewer_*"$VDIG"*_verdict.md \
           2>/dev/null | head -1)
if [ -z "$VERD2" ]; then ... continue; fi
```

Цикл идёт от старшей версии вниз. У **старшей** версии вердикта ещё нет
(заготовка `3.7.3`, до этого — `3.7.2` без вердикта). Тогда:

1. `ls` не находит ни одного файла → **exit 2**;
2. `2>/dev/null` прячет сообщение, но не код;
3. `pipefail` поднимает 2 наверх пайплайна;
4. `set -e` валит шаг **молча** — `[ -z "$VERD2" ]` даже не исполняется.

То есть задуманная ветка «нет вердикта → пропустить и взять следующую версию»
**никогда не выполнялась**. Отсюда парадокс: локально шаг проходил (я запускал
`bash -e`, без `pipefail`), на раннере — падал всегда.

Признак, который я сначала отбросил: `exit code 2` — это не мой `exit 1`
из `::error::`, а код, которым bash выходит при `set -e`/`pipefail`.

## 3. Исправление

Оба подозрительных места переписаны на глоб-цикл встроенного bash —
без внешних команд, поэтому коду пайплайна взяться неоткуда:

```bash
VERD2=""
for F in 00-board/reports/reviewer_*"$VBASE"*_verdict.md \
         00-board/reports/reviewer_*"$VDIG"*_verdict.md; do
  [ -f "$F" ] || continue
  VERD2="$F"; break
done
```

То же для `PKG`.

## 4. Проверено

| Случай | Результат |
|---|---|
| Реальный каталог origin, старшая версия без вердикта (`3.7.3`) | код 0, выбран `3.7.1` ✓ |
| Пакет с вердиктом (`9.9.9` + `reviewer_999_verdict.md`) | код 0, выбран он ✓ |
| Пакет **без** вердикта | код 1, «вердикта нет — пропускаю» ✓ |
| Запуск с `-eo pipefail` (как на раннере) | воспроизведён код 2 до фикса, код 0 после ✓ |
| Реальный прогон на GitHub | **`bd31dcd` success** ✓ |

## 5. Что это значит для остальных

- CI больше не блокирует релиз по причине «Resolve package».
- **Пакет без вердикта по-прежнему не становится релизом** — защита из
  инцидента v3.7.2 сохранена и теперь реально работает (раньше до неё
  не доходило исполнение).
- Строки `JAR=$(ls build-src/build/libs/*.jar | head -1)` (3 шт.) не тронуты:
  они исполняются только после успешной сборки, когда JAR гарантированно есть.

## 6. Цена ошибки

Прогоны на всех коммитах тратили раннеры впустую, а «зелёный CI» до этого
дня не существовал ни разу — то есть предыдущие релизы собирались мимо CI
или руками. Урок: **локальная симуляция обязана повторять флаги раннера**
(`-eo pipefail`), иначе она проверяет не то, что происходит на деле.
