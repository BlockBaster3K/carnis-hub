## Твоя задача СЕЙЧАС — T-3170 · З-17: эталон гейта — из git, а не с диска

**Статус:** ASSIGNED → **IN_PROGRESS** (сразу, без ожидания команды) · **Зона:** `tools/` · **Приоритет 1**

**Почему это важнее остального.** Блоки `glow_check` и `tendril_flesh_match`
(и `alpha_audit --baseline`) берут эталон **из рабочего дерева** —
`01-coder/3.6.0-R/project-3.6.0-R-clean.zip`. У Архитектора он на диске →
`accept_3.7.2.py` → **код 0**. У Ревизора рабочее дерево **без
`3.6.0-R`** (sparse-checkout ради лимита 128 МБ) → те же блоки дают **ложные
✗** (`glow_check` код 1, `tendril_flesh_match` код 2, «8 замечаний»).

**Один и тот же пакет даёт разный вердикт в зависимости от того, как
устроено дерево проверяющего.** Ревизор из-за этого не смог выпустить
вердикт по 3.7.2 и открыл З-17.

**Что сделать:**

1. **Эталон брать из git-объекта**, а не из рабочего дерева:
   `git show <commit>:01-coder/3.6.0-R/project-3.6.0-R-clean.zip` — он есть
   у любого, кто клонировал репозиторий, независимо от sparse-checkout.
2. **Если эталона нет вовсе** (нет клона, нет git, нет файла) — честно
   **«эталон недоступен — проверка пропущена»**, а не **«✗ расхождение»**.
   Пропуск и отказ — разные вещи, и путать их нельзя.
3. **Найти все блоки, читающие эталон с диска** — не только названные:
   `glow_check`, `tendril_flesh_match`, `alpha_audit --baseline`,
   `creature_shade_audit`, `sound_orphans`, `ambient_gate`. Составь
   таблицу: блок → откуда берёт эталон.
4. **Проверить в обе стороны:** пакет 3.7.2 → код 0; и **тот же пакет при
   удалённом `3.6.0-R` из рабочего дерева** → **тоже код 0**, а не ложное
   ✗. Сценарий готовить на копии.
5. **Отчёт** `00-board/reports/integrator_baseline_source.md`.

**Критерий приёмки:** результат гейта **не зависит** от наличия
`3.6.0-R` в рабочем дереве; «эталон недоступен» отличается от «✗
расхождение»; таблица всех блоков — в отчёте.

## Твоя вторая задача — T-3175 · З-18: манифест — рядом с пакетом, не из репо

**Статус:** ASSIGNED → **IN_PROGRESS** после T-3170 · **Зона:** `tools/` · **Приоритет 2**

**Ты закрыл З-17 (эталон из git-объекта).** Теперь — **тот же класс дефекта
в манифесте**, найден Архитектором при проверке пересборки 3.7.2.

**Суть.** `accept_3.7.2.py` / `accept_3.7.1.py` при запуске с **одним**
аргументом (путь к ZIP) берут манифест из **фиксированного пути репозитория**
`01-coder/<вер>/project-<вер>-clean.manifest.txt`. Проверяющий, который берёт
ZIP **из git** (например, с `git show`), получает на **корректном** пакете
«манифест: не сошлось 16 строк» и **код 1** — потому что манифест в его
рабочем дереве старый. С правильным манифестом рядом гейт даёт **код 0**.

То есть **результат приёмки зависит от неучтённого состояния рабочего дерева** —
ровно та же болезнь, что была с эталоном 3.6.0-R.

**Что сделать:**

1. **Манифест по умолчанию брать рядом с ZIP** — из каталога пакета
   (`<каталог ZIP>/project-<версия>-clean.manifest.txt`). Второй аргумент —
   резервный путь, а не единственный способ.
2. **Если рядом нет** — искать в репо по версии каталога (как сейчас); если и
   там нет — честно «манифест не найден», а не «не сошлось N строк».
3. **Проверить в обе стороны:** ZIP + манифест рядом → код 0; ZIP из git +
   старый манифест в репо → **тоже код 0**.
4. **Отчёт** `00-board/reports/integrator_manifest_source.md`.

**Критерий приёмки:** результат гейта не зависит от состояния рабочего
дерева; манифест по умолчанию — сосед пакета.
