## 2. Находки

### З-CI-1 · Вердикт ищется подстрокой, без границ версии

`.github/workflows/build.yml`, шаг «Resolve package»:

```bash
VERD2=$(ls -1 00-board/reports/reviewer_*"$VBASE"*_verdict.md \
            00-board/reports/reviewer_*"$VDIG"*_verdict.md 2>/dev/null | head -1)
```

`VDIG` для `3.1.2` = `312`, а в `00-board/reports/` уже лежит `reviewer_3120_delta_verdict.md` (вердикт про 3.12.0). Пакет 3.1.2 получит **чужой** вердикт и станет релизом. Тот же класс: `3.7` возьмёт вердикт `3.7.1`, `3.7.1` — вердикт `3.7.10`, если такой появится.

Сейчас не стреляет только потому, что пакетов 3.1.2/3.7/3.7.10 не существует. Это вопрос времени, а не гипотеза: файл `reviewer_3120_delta_verdict.md` в репозитории **есть**, и он положительный.

**Предлагаю** (зона Интегратора): сверять не подстроку, а имя целиком —
`reviewer_${VBASE}_verdict.md` или `reviewer_${VDIG}_verdict.md`, то есть перечислить два точных имени вместо двух glob'ов. Если хочется терпеть лишние слова в имени — регулярка с границами: `reviewer_(3\.1\.2|312)_verdict\.md` и никакого `head -1` (при нескольких кандидатах лучше падать, чем угадывать).

### З-CI-2 · `workflow_dispatch` с ручным `package` обходит защиту целиком

Вся проверка вердикта живёт внутри `if [ -z "$PKG" ]`. Если человек (или агент) запускает прогон с `package: 01-coder/3.9.9/project-3.9.9-clean.zip`, шаг не проверяет **ничего** и пакет уходит на сборку и релиз. В инциденте 25.11 спасала только автовыборка; ручной запуск — открытая дверь того же размера.

**Предлагаю:** проверку вердикта вынести **после** вычисления `PKG` и применять к любому пути, включая заданный вручную. Версия для поиска берётся из имени каталога — код уже есть в «Assert version» (`DIR=$(basename $(dirname $PKG))`, `EXPECT=${DIR%%-R*}`).

### З-CI-3 · Пустой файл вердикта считается принятым

Защита устроена как «файл есть и в нём нет отрицательных слов». Значит заглушка (`touch reviewer_399_verdict.md`), случайно закоммиченный пустой файл или вердикт-скелет без выводов дают **зелёный свет**. Отсутствие файла — «не принято», а пустой файл — «принято»: асимметрия не в ту сторону.

**Предлагаю:** требовать в файле явное положительное слово (`ПРИНЯТО`, `ACCEPTED`) **до** проверки отрицательных, иначе пропуск. Заодно это отсекает §3 ниже.

## 3. Правило для меня (и для всех, кто пишет вердикты)

Сценарий 15 показывает: если в **принятом** вердикте встречается фраза «НЕ ПРИНЯТО» (например, «ранее получившие НЕ ПРИНЯТО файлы перечислены в §3»), CI **не выпустит** релиз — сработает fail-safe, но с ложным срабатыванием.

Поэтому мой вердикт по 3.7.2 и все последующие будут содержать слово «ПРИНЯТО» **и не будут** содержать подряд идущих «НЕ ПРИНЯТ», «ОТКЛОНЁН», «REJECTED» — отрицательные случаи описываю иначе («не прошёл», «замечание», «дефект»). Это ограничение на форму, а не на смысл: если пакет плохой, вердикт будет начинаться словами «НЕ ПРИНЯТО» и тогда CI его честно пропустит.

# §5. Перепроверка после правки CI `facb909` — 🔴 шаг по-прежнему падает, но по другой причине

**Дата:** 2026-11-26 · **База:** `b3ba142`

Интегратор исправил один симптом: `grep -q` в условии обёрнут в `|| true` с проверкой `[ -n "$NEG" ]`. Правка верная по смыслу (правило то же), но **причину падения `Resolve package` она не устранила**.

## 5.1. В чём была настоящая причина

GitHub Actions для `shell: bash` запускает скрипт как

```
bash --noprofile --norc -eo pipefail <script>
```

Ключ здесь — **`-o pipefail`**, которого не было в моём прежнем стенде (и, судя по коммиту, не было и в локальной проверке Интегратора). С ним строка

```bash
VERD2=$(ls -1 00-board/reports/reviewer_*"$VBASE"*_verdict.md \
            00-board/reports/reviewer_*"$VDIG"*_verdict.md 2>/dev/null | head -1)
```

падает **всегда**, когда хотя бы один из двух шаблонов не совпал: `ls` пишет `No such file` в подавленный stderr и выходит с кодом 2, `pipefail` поднимает код конвейера, `set -e` убивает шаг. А не совпадает он почти всегда — потому что у вердикта либо вид `reviewer_3.7.1_verdict.md`, либо `reviewer_371_verdict.md`, и второй шаблон в любом случае пуст.

Изолированное воспроизведение (ровно строка из workflow):

```
$ bash -e -c  'V=$(ls -1 00-board/reports/reviewer_*371*_verdict.md 00-board/reports/reviewer_*3.7.1*_verdict.md 2>/dev/null | head -1); echo "V=$V"'
V=00-board/reports/reviewer_371_verdict.md        ← «работает» только без pipefail

$ bash --noprofile --norc -eo pipefail -c '<та же строка>'
$ echo $?
2                                                  ← так падает раннер
```

Это и есть упавший прогон `45629260092/45629091602`: «Resolve package → failure» при живом вердикте и живом ZIP.

## 5.3. Готовый патч, проверенный стендом

`02-reviewer/ci_resolve_package_fix.patch` (102 строки, unified diff против `build.yml` @ `b3ba142`; мой файл, `build.yml` по-прежнему не трогаю — это ваша зона).

Что меняет:

1. **Убирает конвейеры с `ls | head -1`** — вместо них обход по шаблону: `for f in "..." ; do [ -f "$f" ] && ...` — без подоболочки, без SIGPIPE, безопасно под `pipefail`.
2. **Ищет вердикт только по точным именам** `reviewer_<версия>_verdict.md` и `reviewer_<версия без точек>_verdict.md` — это закрывает **З-CI-1** (подстрока: пакет 3.1.2 больше не «находит» вердикт 3.12.0).
3. **Проверяет ручной `package` теми же правилами** — закрывает **З-CI-2** (`workflow_dispatch` больше не обходит приёмку).
4. **Требует явное «ПРИНЯТО»/`ACCEPTED`** в файле вердикта — закрывает **З-CI-3** (пустая заглушка больше не считается принятой).
