# Интегратор: CI выпускал релиз из СТАРОГО пакета (З-CИ-4)

**Дата:** 2026-11-26 · **HEAD при находке:** `2d56b3a` · **Основание:** I6
(«защита от повторного выпуска непринятого пакета: сухой прогон резолвера»)

## 1. Что случилось

Я взялся за I6 — сделать сухой прогон резолвера `build.yml` локально. Первый же
прогон на текущем дереве показал то, чего я не ожидал:

```
⛔ 3.7.3  слово «не принята» (шапка вердикта)
⛔ 3.7.2  слово «отклонён» (шапка вердикта)
✅ 3.7.1  принят
→ CI выберет 3.7.1
```

**CI выбрал бы 3.7.1 — пакет семи версий давности — вместо принятого 3.7.3.**

## 2. Механизм

`build.yml` искал отказ по любому вхождению слова где угодно в файле:

```bash
NEG=$(grep -oiE 'НЕ ПРИНЯТ|ОТКЛОНЁН|ОТКЛОНЕНО|REJECTED' "$VERD2" || true)
```

Но вердикты содержат **историю сдач**. У `reviewer_373_verdict.md`:

```
строка 7:  Цепочка сдач: `d19169b4…` — не принята (правка `pitch` вне S17) →
строка 11: # ПРИНЯТО
```

Строка 7 — про ПРОШЛУЮ сдачу того же пакета. Греп читал её как отказ по
текущему. То же у 3.7.2 («Отклонение | Что не так в 3.7.2» — таблица
исправленного) и 3.5.3 («Пакет `ba14b913…` — НЕ ПРИНЯТО» в истории).

## 3. Доказательство — не рассуждением, а прогоном

Извлёк шаг «Resolve package» **из git** (старую версию) и **из рабочего дерева**
(новую), прогнал оба на реальном дереве:

| шаг | выбранный пакет |
|---|---|
| старый (`HEAD`) | `01-coder/3.7.1/project-3.7.1-clean.zip` |
| новый | `01-coder/3.7.3/project-3.7.3-clean.zip` ✅ |

## 4. Что сделано

**`tools/verdict_decision.py`** — читает РЕШЕНИЕ, а не слово где угодно.
Решением считается строка, начинающаяся с маркера (`ПРИНЯТО`, `НЕ ПРИНЯТО`,
`ОТКЛОНЕНО`, `REJECTED`) после снятия `#`/`*`/`>`, либо
`ВЕРДИКТ|ИТОГ|РЕШЕНИЕ: <маркер>`.

| код | значение |
|---|---|
| 0 | решение отрицательное — публиковать нельзя |
| 1 | решение положительное |
| 2 | решения нет — **fail-closed** |
| 3 | файл не прочитан — **fail-closed** |

`build.yml`: оба грепа (автопоиск и ручной запуск) заменены вызовом скрипта.
Ручная ветка раньше обходила защиту иначе — теперь у них одна логика.

**`tools/ci_resolver_dryrun.py`** — воспроизводит резолвер локально, печатает
какой пакет выберет CI. Коды 0/2/1. Проверяет и то, что вердикт **привязан к
sha256** выбранного ZIP (вердикты цитируют sha сокращённо, поэтому сравнение по
префиксу 12+ символов).

## 5. Проверки

- `02-reviewer/tools/ci_guard_test.py`: **18 сценариев, 0 расхождений, код 0.**
  Пришлось добавить одну строку в `run_step` — тест собирает синтетические
  деревья в tmp, где нет каталога `tools/`; подставляется настоящий путь через
  `VERDICT_TOOL`, а сам шаг читает переменную с дефолтом `tools/...`, то есть
  на раннере поведение не меняется.
- Негативные контроли `verdict_decision.py`: настоящий отказ → 0, отказ через
  `ВЕРДИКТ:` → 0, нет решения → 2, пустой файл → 2, нет файла → 3.
- Пять живых вердиктов (3.7.1/3.7.2/3.7.3/3.5.3/3.6.0) читаются как принятые.
- YAML валиден (`yaml.safe_load`).

## 6. Чего я не делал

`.jar` не собирал, релиз не объявлял, `main` не трогал. Правка меняет только
то, **как читается вердикт**; правила приёмки не ослаблены — наоборот,
отсутствие решения теперь fail-closed, а раньше такой файл считался принятым.

Отдельно: это третий случай за сессию, когда мой инструмент нашёл то, что не
видно чтением. Первые два (громкость через локальную переменную, `path` вместо
`file` в baseline) были моими ошибками. Здесь — дефект в чужом коде, который
работал незаметно, потому что CI не падал: он **успешно** собирал старый пакет.
