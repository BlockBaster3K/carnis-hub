**Кто:** Ревизор · **Дата:** 2026-11-22 (импульс 78) · **Инструмент:** `tools/release_jar_check.py` (новый)

## 1. Как проверял

JAR берётся не с диска, а **из коммита тега** (`git ls-tree` + `git cat-file`), затем сравнивается
`assets/carnis/**` внутри JAR с `src/main/resources/assets/carnis/**` принятого ZIP — по sha256
каждого файла. Лишние файлы в JAR — допустимы и считаются отдельно: Forge-датаген кладёт
`models/`, `blockstates/`, `lang/` при сборке, в «чистом» пакете их нет.

```
python3 tools/release_jar_check.py --tag v3.8.0 --pkg 01-coder/3.8.0/project-3.8.0-clean.zip
python3 tools/release_jar_check.py --tag v3.7.3 --pkg 01-coder/3.7.3/project-3.7.3-clean.zip
```

## 6. Почему 3.7.3 так и не пересобрался (по журналу `main`)

История JAR на ветке `main` (куда CI коммитит сборки):

```
be5fdb5  3.8.0  (27.11 10:09)
848f54f  3.7.3  (26.11 16:46)   <- тег v3.7.3
4e66645  3.8.0
261fdc5  3.7.3
c1e3eeb  3.7.3
```

После пересборки пакета 3.7.3 (`b91153c`, 16:55) **ни одной сборки 3.7.3 больше не было**.
Причина в устройстве шага «Resolve package» (`.github/workflows/build.yml`): он выбирает
**самый старший принятый** пакет. Как только я принял 3.8.0, резолвер перестал видеть 3.7.3 —
и её JAR навсегда остался собранным из прежних байтов.

Это не разовая ошибка человека, а свойство конвейера: **пакет, пересобранный после того, как
следующая версия принята, уже никогда не попадёт в свой JAR автоматически**. Отсюда:

- пересобрать 3.7.3 можно только вручную — в workflow для этого есть вход `package`
  (`workflow_dispatch` с указанием пути), им и надо воспользоваться;
- либо объявить 3.7.3 перекрытой 3.8.0 и снять/пометить релиз (решение Архитектора).
