# Доступ агентов к репозиторию — инструкция и шаблон промпта

Документ для заказчика: как дать каждому агенту (Кодер, Ревизор, Звук, Худ, Архитектор)
самостоятельно сдавать файлы в репозиторий, и как промпт для этого выглядит.

Идея: заказчик **раздаёт промпты**, а файлы агент выкладывает сам — без ручного
скачивания и загрузки через браузер.

---

## 1. Что нужно от заказчика (один раз)

1. Создать **fine-grained PAT** (Personal Access Token → Fine-grained tokens):
   - **Repository access** → Only select repositories → `BlockBaster3K/carnis-hub`
   - **Permissions → Repository permissions:**
     | Разрешение | Уровень | Зачем |
     |---|---|---|
     | Contents | **Read and write** | push своих файлов |
     | Actions | **Read** | видеть прогоны CI и читать их логи |
     | Workflows | Read-only | достаточно по умолчанию |
   - **Не выдавать** `Administration` и `Write` для `Issues`/`Pull requests`, если они не нужны.
   - Срок действия — по необходимости; токен отзывается в любой момент одной кнопкой.

2. Токен **не вставляется в текст промпта**. В промптах ролей стоит плейсхолдер
   `<<TOKEN>>`; заказчик выдаёт токен **переменной окружения** при запуске агента:

   ```
   export GITHUB_TOKEN=<значение>   # в окружении сессии, не в файле
   ```

> Раньше токен вписывался прямо в промпт, и каждая пересборка промптов плодила
> копии секрета в файлах и в контексте агентов. От этого отказались: секрет живёт
> только в окружении, в репозиторий и в промпты не попадает. Держите токен
> fine-grained (только один репозиторий) и отзывайте после завершения цикла.

3. **Альтернатива без токена вообще** — deploy-ключ SSH на каждого агента:
   агент генерирует ключ и присылает публичный, заказчик добавляет его в
   *Settings → Deploy keys* (с правом записи). Безопаснее (токен не утекает в контекст),
   но требует одного действия заказчика на каждого агента и не даёт доступа к API
   (логи CI, релизы).

## 2. Шаблон промпта для агента

Вставьте вместо `{ROLE}` роль агента, вместо `{DIRS}` — его каталоги.

```
Ты — {ROLE} в проекте Carnis (GitHub: BlockBaster3K/carnis-hub).

Ты сдаёшь результат работы САМ, без участия заказчика: файлы нужно положить
в репозиторий самому.

РЕКВИЗИТЫ
  export GITHUB_TOKEN=<<TOKEN>>        # заранее в окружении сессии
  Ветка: arena/d474d740-carnis-hub
  Репозиторий: https://github.com/BlockBaster3K/carnis-hub.git

ПОРЯДОК РАБОТЫ
1. Подготовка (один раз за сессию):
     git clone --depth 1 --branch arena/d474d740-carnis-hub https://github.com/BlockBaster3K/carnis-hub.git
     cd carnis-hub
     mkdir -p tools
     curl -sSL -o tools/agent_push.sh https://raw.githubusercontent.com/BlockBaster3K/carnis-hub/arena/d474d740-carnis-hub/tools/agent_push.sh
     chmod +x tools/agent_push.sh

2. Свою работу веди ТОЛЬКО в своих каталогах: {DIRS}
   Не трогай: STATUS.md, VERIFICATIONS/, 06-build/, 07-project/, .github/, README.md —
   это зона Интегратора. Свои выводы пиши отдельным файлом отчёта в своём каталоге.

3. Перед сдачей проверь сам (правило «не на слово»):
   - каждый файл, который ты сдаёшь, посчитан по sha256 и перечислен в отчёте;
   - если сдаёшь zip-пакет — приложи внешний манифест sha256 (одна строка на файл:
     "<sha256>  <путь>") и проверь, что распаковка даёт ровно столько же файлов;
   - версия в пакете (mod_version) совпадает с версией папки сдачи.

4. Сдача:
     bash tools/agent_push.sh arena/d474d740-carnis-hub \
       "[{ROLE}] <версия>: <что сделано одной строкой>" \
       {DIRS}

   Скрипт сам перебазируется, если за это время кто-то уже отправил изменения.
   Токен не попадает в .git/config и в список процессов.

5. В ответе заказчику укажи: что сдано, sha256 каждого файла, и результат проверок
   из шага 3. Не публикуй токен в отчёте и не коммить его.

ЕСЛИ ТЫ КОДЕР И СДАЁШЬ ПАКЕТ ПРОЕКТА
   Папка сдачи — новая и не переименовывается: 01-coder/<версия>/
   (например 01-coder/3.5.3/, пересдача — 01-coder/3.5.3-R/).
   Внутри: project-<версия>-clean.zip + project-<версия>-clean.manifest.txt + отчёт.
   Имя пакета в папке должно совпадать с номером версии, иначе CI выберет не тот пакет.
   Ранее сданные папки не перезаписывай — создай новую версию.

ЕСЛИ ТЫ НЕ КОДЕР
   Не создавай папки в 01-coder/ — сборку запускает только кодерская сдача.
   Свои файлы клади в свой каталог: 03-sound/, 04-artist/, 02-reviewer/, 05-architect/.
```

## 3. Раскладка по ролям

| Роль | Каталоги | Примечание |
|---|---|---|
| Кодер | `01-coder/<версия>/` | только новая версия; ZIP + manifest + отчёт |
| Ревизор | `02-reviewer/` | вердикт `PhaseF_*.md`; акты в `VERIFICATIONS/` — зона Интегратора |
| Звук | `03-sound/` | банк `.ogg` + манифест; в `06-build/overlay.txt` — только Интегратор |
| Худ | `04-artist/` | PNG/атласы + `SHA256SUMS.txt` |
| Архитектор | `05-architect/` | ТЗ, разборы, блокеры |
| Интегратор | `VERIFICATIONS/`, `STATUS.md`, `06-build/`, `07-project/`, `.github/` | приёмка, акты, overlay, release |

---

## 4. Что происходит при сдаче

1. Агент пушит в общую ветку `arena/d474d740-carnis-hub`.
2. GitHub Actions запускается **сам** — триггер `push` по путям
   `01-coder/**`, `03-sound/**`, `04-artist/**`, `06-build/overlay.txt`.
3. Workflow сам выбирает пакет: последняя папка по `sort -V` в `01-coder/`,
   затем `Assert version` (совпадение `mod_version` с номером папки), `Overlay`,
   `Build`, проверка, что перекрытые файлы попали внутрь jar, публикация релиза
   и коммит jar в `06-build/jars/`.
4. Заказчику остаётся скачать jar и поиграть.

`concurrency` в workflow гарантирует, что при нескольких сдачах подряд собирается
только последняя — промежуточные прогоны отменяются, раннеры не тратятся впустую.

## 6. Что остаётся за Интегратором

Даже при полном доступе агентов одна роль остаётся осмысленной — **Интегратор**:

- **приёмка по хешам**, а не «на слово»: сверка манифеста, распаковки, версии;
- **акты в `VERIFICATIONS/`** — единственный источник правды о том, что принято;
- **`STATUS.md`** — живой указатель потоков; при параллельной сдаче агентов
  его правят в одном месте, иначе конфликты;
- **`06-build/overlay.txt`** — список принятого аудио, попадающего в jar;
- **решение о релизе**: workflow публикует релиз автоматически при каждой успешной
  сборке, поэтому «что считается текущим» должен кто-то один подтверждать.

Агенты при этом сами кладут файлы — заказчику не нужно ничего скачивать и загружать
вручную.
