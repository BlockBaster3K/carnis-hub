### 2.1. Как это выглядело до регистрации (историческая часть)

По промпту сдача идёт **только по SSH**, ключ `carnis-sound` установлен, отпечаток
совпал с ожидаемым:

```
ssh-keygen -lf ~/.ssh/id_ed25519.pub
256 SHA256:k5dHd8aHLgPH4YiZ22Aw2imBRc0RI4c+/8U4coU1+eo carnis-sound (ED25519)
```

Но GitHub ключ **не знает**:

```
$ ssh -T git@github.com
git@github.com: Permission denied (publickey).
$ ssh -T -p 443 git@ssh.github.com          # обход через 443 — то же
git@ssh.github.com: Permission denied (publickey).
$ git ls-remote git@github.com:BlockBaster3K/carnis-hub.git
Please make sure you have the right access rights and the repository exists.
```

`Permission denied (publickey)` — ровно тот случай, который описан в промпте:
**ключ этой роли не был зарегистрирован в GitHub как write deploy key.**

**Что нужно от владельца репозитория** (одна строка, публичный ключ, не приватный;
Интегратор это сделать не может — у его интеграции нет права `administration`,
подтверждено его же отчётом `integrator_ssh_deploy_keys.md`: `403 Resource not
accessible by integration` на `POST /repos/.../keys`):

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIMSrU+s9qlm2tl0+qkOYgu5zgrPZafw+F4CfGsw6dgRJ carnis-sound
```

Зарегистрировать как **write deploy key** на `BlockBaster3K/carnis-hub` и
подтвердить в `00-board/reports/`.

**Чего я не делал и почему:** вариант 2 промпта (`ssh-keygen` нового ключа)
не применял — готовый ключ рабочий и отпечаток верный, проблема не в нём, а в
регистрации. Новый ключ не приблизил бы сдачу ни на шаг, зато плодит неучтённые
ключи. Токен по HTTPS также не использовал: по инструкции «токена нет, он не
нужен и использоваться не должен»; вдобавок оба исторических токена из прошлых
волн GitHub уже отклонил (`Invalid username or token` на запись).

**Чтение при этом работает** (публичный репозиторий), поэтому клон сделан по
HTTPS, а handshake и отчёт лежат локально и будут отправлены первым же push,
как только ключ активируют.
