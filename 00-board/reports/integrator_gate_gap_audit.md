# Интегратор: системный аудит «чекер есть, гейт его не зовёт»

**Дата:** 2026-11-26 · **HEAD:** `8877586` · **Основание:** доска, моя зона
«дыры гейта»

## 1. Зачем

За два дня я дважды находил одно и то же: **проверка написана, работает — и не
подключена**. Сначала `volume_effective_check` (нашёл сам), потом `sample_loudness`
(показал Звук). Решил проверить системно, вместо того чтобы ждать третьего раза.

## 2. Как проверял

Взял все скрипты `tools/*.py` и `02-reviewer/tools/*.py`, оставил только
**проверки** (не сборщики, не отчёты, не утилиты синхронизации) и прогнал на
реальных артефактах — пакете 3.7.3 и банках `sounds/`, `sounds_380/`.

## 3. Что нашлось

| чекер | гейт его зовёт? | что даёт на реальных данных |
|---|---|---|
| `volume_effective_check` | **нет** | код 2 (находка по спеке) — исправлено ранее: блок 9в (отчёт) |
| `sample_loudness` | **нет** | код 2 (разброс 7,7 дБ) — исправлено ранее: блок 9г (отчёт) |
| **`infected_sound_audit`** | **нет** | **код 0** на 132 звуках — **подключён сейчас, блок 9д** |

| `alpha_audit` | через другие блоки | требует `--baseline`, прогоняется как часть светотени |

## 4. Главная находка — 132 звука 3.8.0 никто не измерял

`tools/accept_3.8.0.py` проверял по звукам 3.8.0 **только состав**: «банк =
144 + 132, пакет == банк, имён-пересечений нет». Сами файлы — пик, разброс RMS
внутри категории, crest — не проверялись ничем.

Почему я раньше считал их покрытыми: блок crest работает **от архива З-21**,
то есть считает **дельту к оригиналам**. Это не нормы новых файлов; для 132
новых звуков дельты к «оригиналу» просто нет.

`02-reviewer/tools/infected_sound_audit.py` делает именно это и лежал без
вызова:

```
hurt   файлов 33 | RMS -19.3…-18.9 (разброс 0.3 дБ) | crest 15.8…17.5 | пик -3.36…-1.51
death  файлов 33 | RMS -20.1…-20.0 (разброс 0.1 дБ) | crest 16.6…18.5 | пик -3.47…-1.53
Файлов: 132, провалов: 0, худший пик -1.51 dBFS
ИТОГ: СХОДИТСЯ    код 0
```

## 5. Проверил, что чекер не «зелёный всегда»

Это важнее самого подключения. Плохой чекер в гейте хуже отсутствующего: он
создаёт уверенность.

| прогон | результат |
|---|---|
| как есть | код 0, провалов 0 |
| `--peak -2.0` (файлы с пиком −1,51 обязаны провалиться) | **провалов 21, код 2** |
| `--rms-spread 0.05` | предупреждения 4, код 0 (разброс мягче порога) |
| `--json ...` (привязка к событиям) | код 0 |

То есть порог действительно режет, а не печатается для вида.

## 6. Что сделано

Блок **9д** в `tools/accept_3.8.0.py`: `infected_sound_audit` на
`03-sound/sounds_380` + `sounds_json_infected_33.json`, `need="numpy"`.
Fail-closed: нет чекера или нет каталога — `fail`, а не «пропуск». Нет
`--json` — тоже **fail**: без привязки к событиям проверка неполна, а тихий
пропуск привязки — это то, чем гейт уже болел (З-20).

**Это норма, не отчёт.** В отличие от блоков 9в/9г, здесь критерий не
авторское решение: пик в dBFS, разброс RMS внутри категории и crest — свойства
файлов, проверяемые без спеки и без ссылки на чужой выбор.

## 7. Чего не сделал

**`bank_peak_audit` в гейт не ставил.** Он даёт код 0, но гейт 3.7.3 **уже**
проверяет клиппинг и запас своим блоком 13, и дублировать проверку с другим
порогом (−1,00 против −1,20) значит завести два источника нормы. Если нужно
заменить свой блок на его — это отдельное решение, не «подключение».

**112 остальных скриптов не трогал:** сборщики (`build_3.7.0_assembly`),
отчёты (`sound_metrics`, `volume_decision_table`), утилиты (`inbox_sync`,
`wait_run`, `submit_log`) в гейт не относятся по назначению.
