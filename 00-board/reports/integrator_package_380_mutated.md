# Пакет 3.8.0 изменён после приёмки и после релиза

Заметил при синхронизации: в origin появился коммит Кодера `99fe2ce`
«feat: add optional Curios head/back slots», и в нём — **изменение
`01-coder/3.8.0/project-3.8.0-clean.zip`**.

```
было (принято, вердикт, релиз):  16 994 843 Б   sha256 26edbeefa9dc40f...
стало (99fe2ce):                 16 995 780 Б   sha256 1cb324ba94ebc83a...
```

## 1. Что изменилось по существу

Правка разумная и нужная: необязательная интеграция Curios (слоты head/back).

```
build.gradle         + репозиторий maven.theillusivec4.top
                     + compileOnly/runtimeOnly curios-forge:${curios_version}
gradle.properties    + curios_version=5.9.1+1.20.1
mods.toml            + зависимость на curios, versionRange [5.9.1,)
CarnisMod.java       + регистрация совместимости
CuriosSlotRegistration.java   новый файл
```

Версия внутри осталась `3.8.0` (`mod_version`, `version`, `displayVersion`),
то есть это не 3.8.1 — это доработка уже выпущенной версии.

## 2. Почему это проблема, а не просто факт

Пакет — не рабочий черновик, а **артефакт с закреплённой личностью**:

| где | что закреплено |
|---|---|
| вердикт Ревизора 3.8.0 | sha256 `26edbeef...` |
| `01-coder/3.8.0/project-3.8.0-clean.manifest.txt` | sha256 всех 1037 файлов |
| тег `v3.8.0` → Release | jar `carnis-3.8.0.jar` 17 246 628 Б |
| мой отчёт `integrator_release_380.md` | «jar = принятый пакет, проверено побайтово» |

Теперь ZIP в репозитории **не тот**, что был принят и из которого собран jar.
Любой, кто возьмёт текущий `project-3.8.0-clean.zip` и соберёт из него jar,
получит **другой бинарник**, чем лежит в Release, — с интеграцией Curios,
которую никто не принимал.

Проверил: гейт 3.8.0 на текущем пакете **падает**:

```
1а) Дельта к 3.7.2 — только ожидаемые изменения
  · добавлено 277, изменено 5, удалено 0
      ✗ неожиданные изменения содержимого: build.gradle
  x дельта: есть неожиданные изменения против 3.7.3
ИТОГ: ЕСТЬ РАСХОЖДЕНИЯ — 1
```

То есть репозиторий сейчас в состоянии, где **артефакт выпущенной версии не
проходит собственную приёмку**. Это не «сломалось»: гейт прав, он и должен
падать — изменилось то, что он защищает.

## 3. Особенность нормы, которую это вскрыло

`GROWN_380` разрешает только **добавление** в ресурсные каталоги.
`--allow src/main/java/` разрешает изменения кода. А `build.gradle` и
`gradle.properties` не разрешены **ничем**: они не ресурсы и не java.

Похоже, это не умысел, а пробел: до сих пор зависимости не менялись после
приёмки, и вопрос не возникал. Но пробел двусторонний:

- **минус:** любая законная правка сборки валит гейт выпущенной версии;
- **плюс:** любая **незаконная** правка сборки тоже валит — то есть защита
  сработала, просто она не различает «законную» и «незаконную».

Различать должен человек: решение «правим 3.8.0 после релиза» — архитектурное,
а не механическое.

## 4. Три возможных решения (за Архитектором)

**A. Считать правку частью 3.8.0.** Тогда нужно: новый вердикт Ревизора на
новый sha256, обновление манифеста (сделано), пересборка jar, перезаливка
asset в Release. Тег `v3.8.0` уедет на новый коммит (CI делает `git tag -f`).
Риск: у игроков с уже скачанным jar версия `3.8.0` означает два разных бинарника.

**B. Выпустить как 3.8.1 (или 3.8.0-curios).** Правка получает свою версию,
приёмку и вердикт; 3.8.0 остаётся неизменным и соответствующим своему sha256.
Нужно откатить ZIP в `01-coder/3.8.0/` к `26edbeef` и положить изменённый
пакет отдельно.

**C. Откатить правку из 3.8.0** и вернуть её в работу над 3.8.1. Самое чистое
для выпущенного артефакта, но работа Кодера не пропадает — она ждёт версии.

Рекомендую **B** или **C**: оставлять два разных артефакта под одним номером
версии — это то, что потом невозможно распутать. Уже сейчас мой отчёт о релизе
3.8.0 описывает sha256, которого в репозитории больше нет.

## 5. Что я НЕ делал и почему

- **не откатывал ZIP** — это уничтожит работу Кодера без его ведома;
- **не обновлял вердикт и не трогал тег** — вердикт выносит Ревизор, тег
  привязан к релизу;
- **не пересобирал jar** — Java-компиляция запрещена промптом без отдельной
  команды;
- **не правил `GROWN_380`**, чтобы «разрешить build.gradle» — это ослабило бы
  норму ровно в том месте, где она только что сработала по делу.

## 6. Проверка, что мой блок C не пострадал

На новом пакете `check_core9` по-прежнему работает и даёт то же:

```
Существ: 9, провалов: 26
✗ core9: у существ из игры есть изъяны
```

Смена содержимого пакета на него не повлияла — он смотрит на факты, а не на
sha256.
