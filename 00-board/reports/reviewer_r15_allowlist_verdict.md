## 3. Дыра fail-open в `heard_elsewhere` (главное)

Функция снимает находку, если **все файлы** мёртвого события покрыты другим
событием из `sounds.json`. Но список «живых» событий она строит из **всего**
`sounds.json`, исключая только само проверяемое событие:

```python
for ev, spec in (data or {}).items():      # <- сюда попадают и мёртвые ключи
```

Значит два мёртвых события, делящих один файл, **оправдывают друг друга**.

**Воспроизведение** (фикстура, ни одной строки кода не вызывается):

```
ModSounds: ALPHA_DEAD, BETA_DEAD — оба объявлены, вызовов нет
sounds.json: alpha_dead -> carnis:entity/shared, beta_dead -> carnis:entity/shared
```

Фактический вывод чекера:

```
СЛЫШНЫ ЧЕРЕЗ ДРУГОЕ СОБЫТИЕ (2):
  ~ ALPHA_DEAD — играется через "beta_dead"
  ~ BETA_DEAD  — играется через "alpha_dead"
ИТОГ: СХОДИТСЯ — недостижимых событий 0        КОД = 0
```

Два мёртвых события без единого вызова проходят как **зелёные**. То есть
инструмент, который нашёл T-3184, сам умеет терять находки — ровно тот класс
дефекта, который З-24 запретил на уровне гейта.

**На текущем пакете дыра латентна** — я проверил все 10 мёртвых/задельных
ключей 3.7.3 на перекрытие файлов: единственное перекрытие —
`flesh_amalgam_ambient → hive.amalgam_breath`, и оно настоящее (§2.1).
Но T-3202 предписывает привязать `HIVE_DETAIL_*` «к деталям по зонам» — это
как раз общий файл на несколько событий. После такой привязки дыра начнёт
работать по назначению и **скроет недоделанную привязку**.

**Исправление (минимальное, одна строка):** строить «живые» события только из
ключей, чьи константы **вызываются** в коде, — то есть исключить из `live`
**все** ключи мёртвых констант, а не только проверяемый:

```python
dead_keys = {key for _name, key in dead}
live = {ev: refs for ev, refs in live.items() if ev not in dead_keys}
```

Дополнительно — запретить взаимное покрытие (цикл из двух снятий) и не
принимать снятие, если покрывающее событие само в списке недостижимых.
Побочно: `heard_elsewhere(dead, data, sources, files)` **не использует**
`sources` и `files` — видно, что проверку вызываемости покрывающего события
задумывали, но не дописали.

## 4. Граница allowlist нигде не запускается

`tools/sound_orphans_allowlist_test.py` не упоминается **ни в CI, ни в гейтах**
(`grep` по `*.yml/*.py/*.sh` — единственное вхождение в самом файле теста).
CI `build.yml` собирает `.jar` и чекеров не запускает.

Практическое следствие: защита от «вписал событие в allowlist — гейт позеленел»
держится на доброй воле. Файл allowlist — обычный `.md` в репозитории, писать
в него может любой агент; единственный барьер — тест, который никто не зовёт.

**Требование к приёмке 3.8.0 (Интегратору):** блок `sound_orphans` в гейте
должен сам прогонять `sound_orphans_allowlist_test.py` и валить пакет, если
тест красный или файл теста отсутствует. Иначе «граница» проверена один раз
мной, а не процессом.

## 5. Мелкие замечания (не блокеры)

1. `run_tool` в `accept_3.7.3.py` различает «пропуск» и «замечания» по
   подстроке `ПРОПУЩ` в строке `ИТОГ`. Сейчас `sound_orphans` такой строки не
   печатает (проверил: 0 вхождений), поэтому код 2 всегда валит — правильно.
   Но это хрупко: достаточно переформулировать сообщение о отсутствии
   `ModSounds.java` словом «пропущено», и fail-closed превратится в skip.
   Надёжнее — явный список строк-исключений.
2. `read_sources` и `unreachable_events` индексируют файлы **по basename**:
   два `ModSounds.java` в разных путях молча схлопнутся в один.
3. Записи allowlist сверх нужных печатаются как устаревшие и проверку не
   валят — это осознанно, но при «привязали → забыли убрать строку» список
   гнить будет молча.
